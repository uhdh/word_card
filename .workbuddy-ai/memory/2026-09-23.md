# 2026-09-23 — 언어의 조각 : 말의 심연

## (AH) G1 선택지 재평가 — "값을 치르는 개입"은 **이미 하나 있다**

**계기**: 감독 질문 "G1 에서 뭘 선택해야 해?" — 선택지 셋(일시정지 / 능력 / 타워 판매) 중
무엇을 고를지. 답하기 전에 **각 선택지의 실제 비용**을 코드에서 셌다. 그 과정에서
**G1 의 전제가 두 번째로 틀렸다**는 것을 발견했다.

### 새로 확인한 사실 (전부 코드 실측)

**1. 타워 건설·재건설은 골드도 자모도 쓰지 않는다.**
`DefenseField.update_towers_from_parsed_list()`(`:1232`)는 기존 타워를 `queue_free()` 하고
파싱 결과로 다시 세울 뿐이다. 골드 소비처를 전수로 세면 **딱 다섯**:
발판 구매 · 타일 제거(`TILE_REMOVE_PRICE`) · 타일 교체 · 유물 구매 · 상점 리롤.
→ **"타워 판매"는 지금 구조에서 성립하지 않는다.** 팔고 다시 지으면 골드가 무한히 나온다.
(성립시키려면 경제를 다시 짜야 한다. 그리고 그것은 *비용*이 아니라 *환불*이다.)

**2. 그런데 벨트 편집은 공짜가 아니다 — 숙련이 지워진다.**
- `tower_mastery` 키 = `"%d:%s" % [logical_slot_index, 단어]`
- 웨이브 클리어마다 +1, **상한 5** → 최대 **+25% 피해**(`DefenseField.gd:1163-1171`, `:1261`)
- **슬롯의 단어가 바뀌면 그 키의 숙련을 `erase`** 한다(`:1248`, `:1251`)
- 이동은 안전하다 — 키가 `logical_slot_index` 라서 `tower_positions` 만 바뀌면 유지된다

**3. 그 값은 화면에 없다.**
`숙련` 이라는 문자열은 **UI 코드에 한 곳도 없다**(전수 grep). 타워 툴팁의 시너지 줄에만 붙고,
**정보 모달은 그 라벨을 걸러낸다**(`TowerInfoModal.gd:171`).
→ 플레이어는 **얼마를 잃는지 모른 채** 자모를 끌어낸다.

**4. 일시정지는 기존 메커니즘의 연장이다.**
배속이 이미 `Engine.time_scale`(`TowerDefenseMain.gd:981` `set_speed_scale`) 이므로
일시정지 = `set_speed_scale(0.0)`. 새 콘텐츠 0 · 새 UI 0.
(주의: 트윈은 `time_scale` 을 따르지 않는다 — `TraitImpactProbe.gd:96` 실측.)

### 재평가 결론

| 선택지 | 값 | 판정 |
|---|---|---|
| **일시정지** | 기존 배속의 연장 | ✅ **먼저** |
| **숙련 손실 가시화** | 이미 있는 값에 청구서를 붙임 | ✅ **같이** (신규 콘텐츠 0, 우선 범주에 정확히 해당) |
| 능력 발동 | 자모 소모 = 진짜 기회비용 | ⏸ 3단계 (새 기능 + 난이도 게이트 악화) |
| **타워 판매** | — | ❌ **성립 불가** (무한 골드) |

**권고**: ① 일시정지 → ② 숙련 손실 가시화 → ③ 자모 소모형 개입.
일시정지가 먼저인 이유는 그것이 "값이 없어서 안 하는가 / **시간이 없어서 못 하는가**" 를
갈라 주는 유일한 실험이기 때문이다. 봇은 일시정지를 쓰지 않으므로 감독님이 미뤄 둔
난이도 게이트 작업도 흔들지 않는다.

### 보고서 정정 (`docs/design/04_TD_BENCHMARK_AND_DEPTH_GAPS.md`)

- **§0 에 2차 정정 블록 추가** — "하는 일에 값이 없다" 가 부분적으로 틀렸음
- **§2.4 재작성** — "재배치·재조준·벨트 편집이 전부 무료" 는 틀렸다. 행동별 값 표를 새로 넣고
  골드 소비처 전수 목록과 숙련 메커니즘을 근거로 붙였다
- **§4 G1 재작성** — 진단을 "값이 없다" → **"값이 하나 있는데 보이지 않는다"** 로 고치고,
  선택지 재평가 표 + 권고 3단계 추가
- **§6 진행 상황** — G1 은 이제 "디렉터 승인만 남았다"

### 남은 것
- 감독 승인 대기: G1 3단계 권고 (특히 ①②를 한 커밋으로 갈지)
- 여전히 대기: §2.7 의 `splash` 설명↔로직 불일치 방향, 난이도 게이트 일괄 조정

## (AI) G1 1·2·3단계 구현 완료 — 일시정지 · 숙련 제거 · 밀어내기

감독 지시: **"일시정지 만들고, 숙련 시스템은 제거. 능력 발동도 해줘."**
(②는 원래 "숙련 손실 가시화" 였으나 **시스템 자체 제거**로 바뀌었다)

### 1) 일시정지

- **설계**: `current_speed_scale` **하나**가 진실, `0.0` = 정지. 별도 `paused` bool 을 두지 않는다
  (두면 `set_speed_scale` 과 어긋난다). 재개는 `_speed_before_pause` 로 **멈추기 직전 배속**.
- **입력**: `[P]` 키 + 배속 버튼. **새 버튼을 만들지 않았다** — `btn_speed` 문구가 `⏸ 정지`.
- `start_new_game` 에서 `set_speed_scale(1.0)` 필수(전역 `time_scale` 이라 정지한 채 새 게임 = 정지).

### 2) 숙련(`tower_mastery`) 제거 — 참조 0건

`DefenseField`(변수·`_grant_round_reward` 블록·`erase` 2곳·재적용 4줄) ·
`SaveManager`(**위치 인자 시그니처에서 삭제** + 키 삭제) · `TowerDefenseMain`(3곳) ·
`TowerInfoModal:171` 필터 · `test_wave_balance`(테스트 1개 + 등록 + 주석).
난이도는 **올라가는 방향으로만** 변한다(타워 피해 최대 -25%).

### 3) 밀어내기 (능력 발동)

- **효과**: 경로 위 모든 적을 **경로 길이의 10%** 뒤로. `EnemyUnit extends PathFollow2D` 라
  `progress -= amount` 한 줄이 전부다 — 새 이동 로직 0.
- **값**: **자모 타일 1장 영구 소모.** 자모는 이 게임에서 유일하게 소모되지 않는 자원이었다.
  그래서 "지금을 사는 대가로 다음 단어를 포기" 가 진짜 기회비용이 된다.
- **제한**: 웨이브 중에만, 웨이브당 1회. 값을 먼저 치른다(0마리여도 타일은 안 돌아온다).
- 손잡이 상수 2개: `DefenseField.PUSH_BACK_RATIO`, `TowerDefenseMain.ABILITY_USES_PER_WAVE`.

### ⚠️ 실측으로 잡은 결함 — 트윈은 `Engine.time_scale` 을 **따른다**

`time_scale = 0` 에서 정지 중 벨트를 고쳐 타워를 세우면 등장 연출(0.8→1.0)이 얼어붙어
**타워가 80% 크기로 영구히** 남았다. 직접 잰 값:

| 조건 | 10프레임 뒤 scale.x |
|---|---|
| 그냥 트윈 | **0.500** (전혀 진행 안 함) |
| `set_ignore_time_scale(true)` | **0.880** (정상 진행) |

→ 등장 연출 트윈만 `set_ignore_time_scale(true)`. 배너·섬광·골드 라벨은 그대로 둔다
(멈췄다 이어지면 그만이고, 정지 중 연출이 멈추는 게 맞다).
→ **`tools/TraitImpactProbe.gd:96` 의 "트윈은 time_scale 을 따르지 않는다" 는 다른 조건
(`time_scale=0.1` + `custom_step`)의 관측이다. `time_scale=0` 에서는 성립하지 않는다.**

### ✅ 난이도 게이트를 반복 가능한 도구로 만들었다 (원인은 게이트가 아니었다)

같은 코드로 반복 측정: 남은 HP **50% · 68% · 112%** (합격 2 / 이탈 1). 처음엔 "게이트가 게이트가
아니다" 로 판단하고 초판 근거(`120%`)를 철회했다. **그 철회는 성급했다.**

원인을 파고들어 보니 흔들림의 정체는 게이트가 아니라 **봇이 매판 다른 타일을 받는 것**이었다
(`타워 [도깨비, 절대자, 이마] → 98%` vs `타워 [절대자, 이마, 수비] → 36%`). 즉 이 도구는 난이도가
아니라 **타일 운**을 재고 있었다.

⚠️ **실행 시작에 `seed()` 를 한 번 거는 것으로는 안 고쳐진다** — 실측: 같은 시드 3회 →
타워가 매번 달랐고 **120% / 56% / 88%**. 전역 난수를 게임 내부(지도 생성·크리티컬)가 소비하는
양이 매판 다르고 그 횟수가 프레임 타이밍에 좌우되기 때문이다.

해결: **봇이 입력을 정하는 바로 그 지점에서 시드를 다시 건다** (`seed(bot_seed)` 직후 시작 자모를
다시 뽑고, `_play_policy()` 첫 줄에서 `seed(bot_seed + _round_index())`).

| | 흔들림 (같은 코드 3회) |
|---|---|
| 고치기 전 | 50% · 56% · 68% · 88% · 98% · 112% (**62%p**) |
| 고친 후 (`gate=1`, 시드 자동) | 118% · 116% · 118% (단독 3회) + 120% (스위트) → **116~120% (4%p)** |

→ ⚠️ **0 은 아니다.** 봇의 선택은 고정했지만 게임 내부 난수 소비(지도 생성·크리티컬)가 프레임
  타이밍에 따라 미세하게 달라져 골드가 1~2G 흔들리고, 그게 구매 성공 여부를 바꾼다.
  그래도 **문턱(≤75%)을 넘나들지 않으므로** ±30%p 급 변경은 판정 가능하다.
→ 고정된 입력에서 게임은 **116~120%** — 초판의 "너무 쉽다" **결론은 맞았고 근거만 약했다**.
→ `gate=1` 이면 기본 시드 `DEFAULT_GATE_SEED = 20260923` 자동 적용. `seed=0` 이면 옛 무작위 동작.
→ **부작용**: `TEST_SLOW=1 bash tests/run_all.sh` 가 이제 **결정적으로 RC=1** (게이트가 항상
  `116~120% (≤75% 필요)` 위반). 회귀가 아니라 **거짓 초록이 사라진 것** — 러너는 애초에 게이트
  exit 1 을 스위트 실패로 처리하도록 만들어져 있다(`tests/run_all.sh:68-71`).
  기본 스위트(`bash tests/run_all.sh`)는 여전히 RC=0.
→ **남은 편향**: 봇은 `generate_reward_choices(1)[0]` 로 타일 1장을 뽑는다 — 실제 게임의 3택1
  드래프트(2번째가 항상 모음 보장)를 보지 못한다. 그래서 게이트 수치는 **보수적**(실제보다 어렵게)
  이다. 고치면 기준선이 통째로 움직이므로 별도 결정 사항.

### ⚠️ 벨트 헤더는 이미 꽉 찼다

밀어내기 버튼을 헤더에 넣었더니 미리보기 라벨이 **568→486 / 479→397 px** 로 줄고

→ 버튼을 **톱바 2번째 줄(`MonsterColumn`) 오른쪽 끝**으로 옮겨 568 / 479 px 복구, 잘림 0건.
→ 헤더에 앞으로 더 넣으려면 **헤더 2줄화**(타일 영역 ~28 px 감소)가 필요하다. 감독 결정 대기.

## (AI) §2.11 발견 — 막 클리어 모달이 축하하는 동안 다음 막이 이미 출발한다

감사 §5.2 의 9번("모달 동안 웨이브 시작 보류")이 **미집행**임을 확인했다. §6.8 이 "미검증"으로
남겨 둔 항목이고, 이제 코드 + 실측으로 **아직 그렇다**는 것이 확정됐다.

**`TowerDefenseMain._on_act_cleared` (`:908`)**
```gdscript
	_show_modal(modal)          # ① 중앙 480×260 패널
	_start_wave_automatically() # ② **바로 다음 줄**에서 다음 막 웨이브 시작 (카운트다운 없음)
	...
	get_tree().create_timer(3.0).timeout.connect(...)  # ③ 3초 뒤 자동 닫힘
```

세 가지가 겹친다:
1. **모달이 경로를 덮는다** — `PRESET_CENTER` + 480×260. 캡처 확인: 보드 중앙이면 경로 S자
   중간 구간을 통째로 가린다. 그 뒤에서 적이 걷고 있다.
2. **닫기 버튼이 없다** — 제목·본문뿐. 닫는 수단은 3초 타이머 하나.
3. **그 3초가 `Engine.time_scale` 을 따른다** — `PauseAbilityProbe` 로 실측:

| 조건 | 3.0초 타이머 실제 |
|---|---|
| `time_scale = 4.0` 그냥 | **766 ms** |
| `time_scale = 4.0` + `ignore_time_scale=true` | **3029 ms** |
| `time_scale = 0.0` 정지 | **발화 안 함** |

→ 4x 플레이어는 막 클리어 문구를 **0.77초**만 보고, 정지 중엔 모달이 안 닫힌다(탈출구는 배속 버튼뿐).
→ 모달 동안 적 진행: 2막 기준 일반 85px/s · 질풍 165px/s → **3초에 255px · 495px**.
  배속이 몇이든 **게임 안 거리는 같다**(모달 수명과 게임 속도가 함께 배율을 탐) — 달라지는 건
  **플레이어가 읽을 시간**뿐이다.

**고칠 재료는 이미 있다**: `_is_terminal_modal_open()`(`:640`)이 "종료성 모달이 떠 있다" 를 이미

**⚠️ 같은 질문**: `GAME_FEEL_AUDIT.md` §5.4 가 "보스 등장 예고: 게임 진행을 멈춰야 함 →
설계 결정 필요" 로 미뤄 둔 그 질문이다. 다만 **일시정지가 이미 생겨서** 그때보다 비용이 낮다.

`render_belt()` 의 '새 단어' 판정이 **서식 붙은 문자열과 맨 음절을 비교**하고 있었다:
`_last_parsed_words` 에는 `"[가 타워]"` 가 들어가는데 `has(syl)` 은 `"가"` 로 묻는다 →
**항상 false** → `new_words` 가 매 렌더마다 '완성된 단어 전부'.
**완성음을 그냥 연결했으면 타일 드래그 · 회전 · 구매마다 징글이 울렸다** — 침묵보다 나쁘다.
고침: `_last_parsed_words` 에 **음절**을 담고, 서식은 라벨 전용으로 분리.

**`tools/CelebrationProbe.gd` 신규** (headless, ~4초). **양방향**으로 잰다 —
진짜 완성하면 배너 **1**(0이면 연출이 죽은 것), 상태 안 바꾼 재렌더는 **0**(고치기 전 1).
**주입 실험으로 둘 다 확인**: 연출을 죽이면 `on_completion=0` 으로 실패, 판정을 되돌리면
`unchanged_rerender=1` 로 실패.

**도구 첫 판이 헛통과했다** — '단어가 파싱됐는가' 를 `parsed_preview_label.text.contains("타워")`
로 봤는데, 그 라벨의 **고정 접두사가 `"자동 완성 타워: "`** 라서 아무것도 파싱 안 된
`"자동 완성 타워: 단어 조합 없음"` 에서도 참이었다. **아무것도 재지 않고 통과.**
지금은 `parsed_slots()` 를 센다. → **전제 조건은 표시 문자열이 아니라 메커니즘을 읽어야 한다.**

2. **효과를 사건에 연결하기 전에 그 사건의 '발화 조건' 이 실제로 구분되는지 확인하라.**
   §2.12-a 가 정확히 그 사례다. **함수 이름은 근거가 아니다.**
3. `_is_terminal_modal_open()` 은 **이름이 거짓말**이다(모든 모달).
4. 모달이 '다음 행동' 을 소유하면 `_close()` 를 노출해야 봇이 같은 문을 지난다.

## §2.11 잔여 구멍 봉합 + 도구 위생 (2026-09-23 후속)

디렉터의 "너가 좀 알아서 해줘" 에 따라, §2.11 에서 **디렉터 판단으로 남겨 두었던 우회 구멍**을 닫았다.

### 한 일

- **Space·상단 [웨이브 시작] 우회 봉합** (`TowerDefenseMain.gd`): `_act_clear_modal` 참조 + 좁은
  술어 `_act_clear_modal_open()`, 그리고 `_on_start_wave_pressed()` 최상단에서 술어가 참이면
  `_close()` 로 **라우팅**한다(막지 않는다 — 프로젝트 규칙 "조용히 아무 일도 안 일어나면 버튼이
  고장 난 것처럼 보인다").
- **순서 계약**: `_on_act_clear_dismissed()` 가 참조를 **콜백 전에** 비운다. 뒤집으면 모달이
  스스로의 시작을 막아 웨이브가 영영 시작되지 않는다(주입 RC=5 로 확인).
- **불러오기 정리**: `_on_load_pressed()` 가 모달을 넘겨받지 않는다. 남겨 두면 그 버튼이 로드된
  웨이브를 **하나 건너뛴다**(`start_next_wave()` 가 `current_wave` 를 증가시킨 뒤 시작).
- `start_new_game()` 의 모달 일괄 정리에서도 참조를 비운다.

### 검증 (전부 주입으로 반증)

| 주입 | 결과 |
|---|---|
| 라우팅 제거 | RC=2 — `modal_closed=false` 인데 웨이브 시작 |
| 콜백 순서 뒤집기 | RC=5 — `모달이 스스로의 시작을 막았다` |
| 로드 정리만 제거 | RC=2 — 그 두 단언만 실패(독립성 확인) |

### ⚠️ 새로 나온 함정 (중요)

1. **`SaveManager._is_test_run()` 은 이름 화이트리스트다** — 새 프로브를 등록하지 않으면
   **플레이어의 실제 세이브를 향한다.** `ActClearModalProbe` 는 `delete_save_file()` 까지 부르므로
   조건이 맞으면 실제 세이브를 **지운다**. → `a.contains("/tools/")` 경로 규칙을 위에 추가했다.
2. **⚠️ `user://` 는 실행 환경에 따라 달라진다.** 이 저장소의 bash 셸은 **`APPDATA` 가 비어 있어**
   Godot 가 `user://` 를 **프로젝트 안쪽 `./Godot/app_userdata/`** 로 떨어뜨린다
   (`ProjectSettings.globalize_path("user://")` → `./Godot/app_userdata/...`).
   즉 이 환경에서 프로브가 안전했던 것은 **다른 파일을 보고 있었기 때문**이지 등록 때문이 아니다.
   → 파일 경로를 bash 로 검증할 때는 **Godot 안에서 globalize 한 경로**를 기준으로 삼아라.
3. **`godot/Godot/` 이 git 에 untracked 로 6.4MB 쌓여 있었다**(app_userdata 6.3MB, `hint_*.png`·
   `t*.png` 각 ~930KB). `.gitignore` 에 `.godot/` 만 있었다.
4. **⚠️ `core.ignoreCase = true` 인 저장소에서 `**/Godot/` 를 무시하면 게임 본체 `godot/` 까지
   삼킨다.** 산출물 항목만 하나씩 적고 `git check-ignore` 로 확인해야 한다.
5. **프로브의 후보 검색이 부분 파싱을 '완성' 으로 받아들였다** — `_tower_count > 0` 만 보면
   `가속` 을 노렸는데 `가` 만 나와도 통과한다. `_parsed_text(belt) == w` 로 전체 단어를 요구하도록
   고쳤다(이름 붙인 사건을 실제로 재게).
6. **⚠️ 프로브가 주변 상태를 물려받았다 — 코드를 안 바꿨는데 실패.** `ActClearModalProbe` 는
   `reset_combat_state()` 만 불러 기준선을 잡았는데, 게이트를 돌린 뒤 남은 테스트 세이브가
   `3막 20라운드` 라서 `start_next_wave()` 가 시작할 막이 없었다 → **RC=3 거짓 실패**.
   (최종 검증을 한 번 더 돌린 덕에 발견했다.) `start_new_game()` 으로 기준선을 고정하고
   `current_act == 1` 을 단언하도록 고쳤다 — 연속 2회 동일한 `wave_before=1`.
   **세계를 고정하지 않고 읽는 프로브는 코드가 아니라 그때그때의 기계를 잰다.**

### 남긴 것 (디렉터 판단)

- 두 프로브를 `tests/run_all.sh` 에 **등록하지 않았다**: 러너는 `passed` 줄을 요구하고
  (`RESULT_RE`), 프로브가 테스트 도감·세이브를 변형해 순서 의존을 만든다.
- 게이트 재측정은 이번 변경으로 **움직이지 않아야 한다**(봇 경로는 `_clear_modals()` → `_close()`
  로 이미 같은 문을 지나므로).

## 저체력 맥동 트윈 누수 — 감사 §2.11 항목 8 (2026-09-23, 이어서)

감사 문서 §6.8 이 "미검증" 으로 남겨둔 마지막 코드급 항목. `_update_low_hp_warning()` 의
`else` 가 트윈을 죽이지 않아 **위험 구간을 벗어나도 계속 맥동**하고, 재진입마다 트윈이 쌓였다.

### 실재했다 — 나가는 경로가 넷

| 경로 | 위치 |
|---|---|
| 회복의 향로 (+2) | `DefenseField.gd:1179` |
| 방어+회복 인접 (+1) | `DefenseField.gd:1184` |
| 철옹성 룬 (+10 최대 / +10 현재) | `TowerDefenseMain.gd:1014` |
| 불러오기 (뚫린 횟수 환산) | `TowerDefenseMain.gd:359` |

### 고침

`var _low_hp_tween: Tween = null` 멤버 추가. 해제 시 `kill()` 후 `modulate = Color.WHITE`.
메타 가드(`has_meta("_low_hp_pulsing")`)를 `is_valid()` 가드로 교체 — 메타는 노드에 붙어
재진입 때마다 새 트윈을 만들었다.

### 실측 (`tools/LowHpWarningProbe.gd`, 헤드리스, 2회 동일)

| 단언 | 고침 전 | 고침 후 |
|---|---|---|
| §0 기준선 | 트윈 0 · span 0.000 | 트윈 0 · span 0.000 |
| §1 진입 | 트윈 생성 · span 0.249 | 트윈 생성 · span 0.249 |
| §2 회복 | **트윈 생존** · span 0.235 | 트윈 사망 · span 0.000 |
| §3 재진입 | **트윈 2개** | 트윈 1개 |
| §3b 머무는 동안 신호 5회 | 트윈 2개 | 트윈 1개 |

### 이번에 새로 배운 함정

1. **⚠️ 누수 판정을 애니메이션되는 속성의 시간축 측정으로 하면 거짓 통과가 난다.**
   트윈이 둘 이상이면 같은 속성을 번갈아 밀어 **합성값**이 되고, 0.5초 동안 붙박이인 것처럼
   보인다 — 실측 `lo=0.7500 hi=0.7526` 인데 **바로 다음 창은 `0.2444`**. 판정은 **트윈의 생사**
   (`Tween.is_valid()` / `get_tree().get_processed_tweens()`)로 하고, 시간축 측정은 트윈이
   **하나뿐인** 구간에서만 쓴다. 기준선도 먼저 고정한다(장면에 이미 트윈이 있으면 델타가 거짓).
2. **⚠️ 상태 플래그로 재면 안 된다.** `has_meta("_low_hp_pulsing")` 는 누수 상태에서 **깨끗하다**
   — `else` 가 플래그는 지우고 트윈은 놓아주기 때문. **상태가 아니라 자원의 생사를 재라.**
3. **⚠️ '상태에 머무는 동안' 경로를 단언해야 한다.** 진입/재진입만 재면 가드 제거 주입이
   **통과한다** — 가드가 없어도 재진입은 트윈을 하나만 만든다. 누적은 신호가 **안에서 반복될 때**
   일어나고 그게 실전에서 가장 흔한 경로다(적이 새어 나갈 때마다 신호). §3b 를 추가한 뒤에야
   `live_tweens=6` 으로 잡혔다.
4. **검증 안 한 순서 주장을 주석에 쓰지 마라.** 첫 초안 주석이 "`kill()` 과 색 복원의 순서가
   중요하다" 고 적었는데 **거짓**이다 — 같은 호출 안에서 동기적으로 일어나 프레임이 끼어들지
   않는다. 주석을 고쳤다. "설명이 계약" 규칙에서 **거짓 주석 자체가 결함**이다.
5. **§4 가 덤으로 드러낸 것**: 전멸(ratio 0) 상태에서 기지 표시가 흰색이 아니라 **붉은 맥동
   중간값에 붙잡혀** 있었다 → 게임오버 화면 뒤에서 기지가 계속 붉게 흔들리고 있었다.

### 남긴 것

## 보스 등장음 — 감사 §2.4 (2026-09-23, 이어서)

감사 §5.1 의 마지막 "1줄" 항목. 보스 등장은 시각 연출 5종(흔들림 2 + 붉은 섬광 + 배너 +
실루엣 1.9배 + 전용 HP바)을 동원하면서 **무음**이었다 — `_juice_boss_entrance()` 에
`SoundEngine` 호출 0건.

### 재사용하지 않은 이유 (핵심 판단)

`play_wave_start()` 를 재사용하면 안 된다. 그 소리는 **`TowerDefenseMain.gd:1071` 한 곳에서만**
불린다 — 즉 **매 웨이브**. 보스에 쓰면 "다음 웨이브 시작" 과 똑같이 들리고, 그 웨이브는
이미 5라운드 전에 시작됐다. **침묵보다 나쁘다 — 거짓 신호다.**
(`play_hit` 은 4곳에서 불려 전투 소음에 묻힌다.)
→ **보스 전용음** `SoundEngine.play_boss_entrance()` 를 새로 만들었다.
세트 최장(0.75초 vs 웨이브 시작 0.5초), 낮은 음을 **유지**(110→82.41Hz 각 0.35초),
어택 0.1초(세트의 나머지는 전부 즉시 어택이라 이것만 '다가온다' 로 들린다).

### ⚠️ 감사 주장 #3 을 철회했다 — 재보니 틀렸다

감사 §2.4 는 "보스가 2마리인 라운드면 연출이 2번 겹친다" 고 적었고, 고침은 ~3줄
("라운드당 1회" 가드)로 보였다. **실측하니 거짓이었다** — 보스 1마리, 배너 1개.
`_build_wave_monsters()` 가 보스를 한 번만 큐에 넣고, `start_next_wave()` 가 `is_wave_running`
으로 자기 중복을 막는다. → **가드를 넣지 않았다.** 도달 불가능한 가드는 죽은 코드다.
**감사는 가설이고, 프로브가 판정이다.**

### 실측 (`tools/BossEntranceProbe.gd`, 헤드리스, 2회 동일)

| | 값 |
|---|---|
| 보스 라운드 (1막 5R) | 큐 8개 = 보스 1 + 잡몹 7, 보스가 `queue[0]` |
| 스폰 후 | `bosses=1 banners=1` |
| 소리 | `boss=0.75s zcr=189` / `wave=0.50s zcr=596` |

주입 반증: 소리 호출 제거 → **RC=2**, 보스음을 짧고 높게(0.3초·440Hz) → **RC=2**.
스위트 6종 **RC=0**.

### 새로 배운 함정

1. **⚠️ 무음 이벤트에 소리를 붙일 때, 후보 소리가 그 이벤트 전용인지 먼저 세라.**
   `grep -rn 'SoundEngine\.play_[a-z_]*' scripts/` 로 호출 수를 보고, **다른 반복 이벤트에
   쓰이는 소리는 재사용 금지** — 정보가 사라진다.
2. **⚠️ "소리가 났는가" 를 헤드리스로 재는 법**: `SoundEngine._cached_streams.has(name)`.
   단 **`SoundEngine.muted = false` 를 먼저** 해야 한다 — `_play_synth_stream()` 첫 줄이
   `if muted: return` 이라 합성조차 안 되어 단언이 아무것도 재지 못한다. `muted` 를 직접
   대입하면 `_save_config()` 를 안 지나므로 플레이어 설정 파일이 안전하다.
   기준선도 고정한다(오토로드는 프로세스 내내 살아 있으므로 낡은 캐시가 통과를 위조한다).
3. **영교차율 = 8비트 합성음의 피치 대리 지표.** `crossings * mix_rate / data.size()`.
   난수 없는 합성이면 결정론적이라 단언에 써도 된다(189 vs 596, 3배 차).
4. **⚠️ 측정한 것보다 많이 주장하지 마라.** 처음 주석에 "세트에서 가장 낮고 가장 길다" 라고
   썼는데 **거짓**이었다 — `play_hit()` 이 40Hz 까지 내려간다(0.12초 스침). 주석을
   "가장 길고, 낮은 음을 **유지**한다" 로 정확히 고쳤다. 앞서 철회한 게이트 "116~120%" 와
   같은 규율.
5. **`BossBar` 로는 중복을 못 센다** — `_attach_boss_bar()` 가 이전 것을 free 하므로 언제나
   ≤1. **곱해질 수 있는 노드**(`BossBanner`)를 세라.

### 남긴 것

- §2.4 문제 2 (`Juice.shake` 2개 노드 위상 불일치)와 문제 4 (예고 부재)는 **미해결**.
- 청감(사람이 실제로 어떻게 들리는가)은 여전히 미검증 — 프로브는 **합성 여부와 파형**만 잰다.

## SFX 겹침 스로틀 + 피치 지터 — 감사 §5.1 항목 5 / §2.12 (2026-09-23, 이어서)

감사 §5.1 의 5번. `SoundEngine._get_player()` 가 **재생 중이 아닌** 플레이어를 주므로,
같은 소리를 한 프레임에 N번 부르면 **N개 플레이어가 같은 파형을 동시에** 재생한다.
파형이 같으니 위상까지 맞아 **단순 합산** → `20*log10(N)` dB. 실측 5회 = **+14.0 dB**.
저작된 음량이 아니라 "그 순간 몇 마리를 맞혔는가" 가 음량을 정하게 된다.

### 실재 경로 (추론 아님)

`Meteor._impact()`(`Meteor.gd:55-68`)가 폭발 반경의 **모든 적**을 순회하며
`enemy.take_damage(damage * mult, true, mult)` 를 부른다 — **두 번째 인자가 소리 켬**이다.
적 5마리 → 한 프레임에 `play_hit()` 5번. (`Projectile` 의 광역은 `false` 라 면제 — 불리언을 봐라.)
`play_coin()` 도 대량 사망에서 같은 구조.

### 잠금 창을 실측으로 정했다 (50ms)

가장 빠른 **정상** 반복 = 연사 타워의 공격음. 최악 간격은 보정 5개가 곱해진다:

| 인자 | 값 |
|---|---|
| `TRAIT_INTERVAL["rapid"]` | 0.3 |
| `INTERVAL_MULT_BY_LENGTH[2]` | 0.70 |
| 모양 `speed_pct_to_interval(4)` | 0.9615 |
| 유물 `speed_pct_to_interval(18)` | 0.8475 |
| `speed_pct_to_interval(20)` | 0.8333 |
| **곱** | **≈0.119초** |

→ 50ms 는 **2.4배 여유**. "느낌상 안전한 값" 이 아니라 계산해서 고른 값이다.
덤 확인: `_play_attack_sound()` 는 공격당 **1회**(`WordTower.gd:596`, 발리 루프 613 **앞**)
→ 3연발이 소리를 3배로 만들지 않는다.

### ⚠️ 새로 배운 함정

1. **⚠️ 두 줄짜리 계약에는 두 줄짜리 프로브가 필요하다.** 첫 프로브는 스로틀만 쟀다.
   그 상태로는 `randf_range(0.96, 1.04)` 를 `1.0` 으로 바꿔도 **통과했다** — 계약의 절반이
   무방비였다. §5 를 추가한 뒤에야 RC=1 로 걸렸고, **§5 가 유일한 방어선**임이 주입으로 증명됐다.
   **고침에 절이 둘이면, 프로브에 절이 둘인지 세라.**
2. **⚠️ 지터는 범위와 변화를 둘 다 재야 한다.** "값이 다르다" 만 재면 **±40% 변조**도 통과한다
   — 그건 지터가 아니라 다른 소리다. `0.96 ≤ p ≤ 1.04` **그리고** `max−min > 0`.
3. **⚠️ 전역 초크포인트를 건드리면 스위트 전체를 돌려라.** 모든 소리가
   `_play_synth_stream()` 을 지나므로 실수는 국소적이지 않다. 게다가 배포 전에
   `grep -rn 'SoundEngine\.play_[a-z_]*()' scripts/` 로 **같은 프레임 같은 이름 중복**을
   감사해야 한다. 이 프로젝트의 근접 쌍들은 전부 **상호배타 분기**였다(early `return` ·
   `if/else` · `match` · 버튼 핸들러) — **읽어서 확인했지 가정하지 않았다.**
4. **⚠️ `_drain()` 이 창을 넘기는 건 우연이다.** 소리 길이(0.12초)만큼 기다려서 그런 것뿐이라,
   누가 소리를 짧게 만들면 조용히 깨진다. 보장이 필요한 절은 `create_timer(0.08)` 로 **명시**한다.
5. **플레이어 수는 스트림 동일성으로 세라** (`p.playing and p.stream == 캐시`), `pitch_scale` 도
   **그 스트림을 재생 중인** 플레이어에서 읽어라 — 아무 플레이어나 고르면 안 된다.

## 런의 마지막 문장에 소리 — 감사 §2.8 / §5.2 항목 10 (2026-09-23, 이어서)

**§5.1 의 8항목이 전부 닫혔다.** 다음 구간 §5.2 로 넘어가, 그중 효과 "높음" 인 10번을 잡았다.
사용자 본인의 지적("승리는 되지만 감정적인 마침표가 없음")과 직결된 항목이다.

### 진단 — 무음이 아니라 **배분**이었다

`_on_game_over()` 에 `SoundEngine` 호출이 **0건**이었다(승리·함락 둘 다). 60라운드를 끝낸
순간도, 기지가 함락된 순간도 무음. 반대로 `play_victory()`(0.4초 4음 상행)는
`DefenseField._grant_round_reward()` 에서 **라운드가 끝날 때마다**(런당 수십 번) 울리고 있었다.

→ **런당 1회인 최상위 사건은 무음, 런당 수십 회인 사건이 클라이맥스음을 쓰고 있었다.**
§5.5 "연출이 잘못 배분되어 있다" 의 가장 선명한 사례. **"여기 소리가 있나?" 가 아니라
"빈도 양 끝을 비교하라"** 로 찾았다.

### 고침

| 소리 | 길이 | 모양 | 쓰이는 곳 |
|---|---|---|---|
| `play_final_victory()` | **0.95초** | 6음 **상행** C5→G6 | 런 승리 |
| `play_defeat()` | **0.80초** | 4음 **하행** G4→G3 | 기지 함락 |

보스 등장음에서 `play_wave_start()` 를 거부한 것과 같다 — 그 소리는 이미 "또 한 라운드
끝났다" 라서, 승리에 쓰면 런의 마지막 순간이 그와 구별되지 않는다(**침묵보다 나쁜 거짓 신호**).

**런 승리 0.95 > 함락 0.80 > 보스 0.75 > 웨이브 시작 0.50 > 기존 승리 0.40**

### ⚠️ 가드 하나가 이 고침의 본체다

이름이 달라 스로틀도 못 막는다(그냥 합산된다, `SfxStackProbe` 가 잰 현상).
→ `if not (is_act_final and current_act >= MAX_ACTS):` 로 3막에서만 건너뛴다.

## Phase E — 보상 카드 → 벨트 획득 연출 (§2.6 문제 2) — 2026-09-23

1. **`add_jamo()` 를 연출에 맞춰 늦추지 않는다.** 상태 변경을 연출에 미루면 그 사이 벨트를
   건드리는 다른 경로(드래그·구매·회전·불러오기)와 어긋난다. **연출이 상태를 따라간다.**
2. **고스트를 `modal_layer` 에 넣지 않는다.** `_is_terminal_modal_open()` 이
   `modal_layer.get_child_count() > 0` 이라 **모든 모달**을 참으로 돌려준다 → 거기 넣으면
   연출이 사는 0.28초 동안 다음 모달이 막힌다. `main` 자식 + `z_index=100`.
3. **레이아웃은 다음 프레임에 확정된다.** `add_jamo()` 직후 타일 rect 를 읽으면
   `HFlowContainer` 가 아직 배치를 안 해 **(0,0)** 이 나오고 연출이 화면 좌상단으로 날아간다.
   한 프레임 기다린 **뒤** 도착점을 조회한다. 노드를 미리 잡아 두지 않는 이유도 같다 —

→ 그래서 18번(disabled 사유)을 골랐다. **"코드가 아는 것을 화면이 안 보여 주는"** 전형이고,
그 이유를 아는 코드가 **판정과 함께 계산된 뒤 그 줄에서 버려지고** 있었다.

### 무엇을 고쳤나


판정과 사유를 **한 곳에서** 만든다 — **사유가 곧 판정**이 되게 해서 둘이 어긋날 수 없게 했다.
`_button_state(price, empty_belt_blocks) -> {"disabled", "reason"}` + `_with_reason(base, reason)`.
사유는 툴팁에 붙인다 — 버튼 **글자**를 늘리면 벨트 헤더가 조용히 잘리고(`clip_text`),
이 벨트는 이미 툴팁을 쓰고 있었다(구매 버튼의 시세 안내).

**덤으로 잡은 것**: 용량 `30` 이 **세 곳에 흩어져** 있었다 — 비활성 **판정**
(`_update_buy_buttons`) · 실제 **삽입**(`add_jamo`) · 구매 **게이트**
(`TowerDefenseMain._on_tile_purchase_requested`). 한 곳만 고치면 **버튼이 거짓말을 한다**
(눌리는데 안 담기거나, 담기는데 안 눌린다). `JamoBelt.MAX_BELT_TILES` 로 모았다.
⚠️ `JamoBelt.gd:21` 주석은 **이미** "벨트가 꽉 차면(30장)" 이라고 적고 있었다 —
**규칙은 문서에만 있고 코드에는 없었다.**

## Phase G — 누른 순간이 호버와 구별된다 (§5.2 17) — 2026-09-23

### 왜 이 항목인가

**디렉터가 직접 지적한 항목**이다 — *"버튼은 작동하지만 눌렀다는 반응이 없음"*(§2.10 문제 1).
원인은 **한 줄**이었다:

```gdscript
btn_tile.add_theme_stylebox_override("hover",   hover_style)
btn_tile.add_theme_stylebox_override("pressed", hover_style)   # ← **같은 객체**
```

`pressed` 에 호버 스타일을 그대로 넘겨서 **누르고 있는 동안 화면이 호버와 완전히 동일**했다.
스타일박스를 안 만든 게 아니라 **만들 필요가 없다고 착각한** 형태다(두 줄이 같은 변수를 쓴다).

### 방향은 **테마에서 읽었다** — 새로 정하지 않았다

`ui/theme/game_theme.tres` 를 파싱해 보니 이 프로젝트의 `Button` 관례가 명확했다:

```
Button  normal 0.102 → hover 0.141 → pressed 0.055   (호버에서 밝아졌다가 누르면 어두워진다)
GhostButton  normal 투명 → hover 0.141 → pressed 0.055(함몰색으로 **채운다**)
PrimaryButton normal α0.25 → hover α0.42 → pressed α0.62 + 흰 테두리
```

**누름은 언제나 '더 들어간' 상태**다 — 그래서 타일도 `darkened(0.28)` 로 간다(호버 `lightened(0.12)`
와 **반대 축**). 테두리는 normal 값으로 되돌려 호버와 **두 축**이 달라지게 했다.
선택 상태(`lightened(0.18)` + 금색 3px)와도 겹치지 않는다.

### 슬롯 버튼(고정/힌트) 6개에도 같은 결함 — 여기서 한 번 더 걸렸다

비활성일 때 `bg` 가 **투명**이라 `darkened()` 로는 **아무 변화가 없다.** 그래서 테마의
`GhostButton` 처럼 **`BG_INSET` 으로 채운다**. (`pressed_bg := bg.darkened(0.30) if active else Palette.BG_INSET`)

### 의도적으로 제외한 것 — 회전 배지

`pressed` 가 비어 있는 게 **맞다**: (1) 회전은 누르는 즉시 글자가 바뀌어 **결과 자체가 피드백**이고,
(2) 26x26 은 **투명 클릭 영역**이라 눌림 상자를 그리면 타일 모서리에 상자가 뜬다 —
배지를 34px→26px 로 줄인 이유와 정면 충돌한다. **코드에 그 이유를 주석으로 못박았다**
(다음 사람이 "빠졌네" 하고 채우지 않도록).

### 실측 (`tools/TilePressProbe.gd`, 헤드리스, 2회 동일 — 상대 휘도)

```
타일     normal=0.130 hover=0.234 pressed=0.094  hover_a=0.95 press_a=0.95
슬롯×6   normal=0.000 hover=0.000 pressed=0.051  hover_a=0.00 press_a=1.00
rotate_badge pressed=비어 있음 (의도적 배제)
```

### ⚠️ 배운 것 1 — 프로브가 **채널을 고정하면 멀쩡한 위젯이 실패한다** (내 실수)

### §5.2 21 — 같은 숫자가 두 문구로 두 번 보였다 ✅

`_process()` 가 **같은 값**을 두 라벨에 쓰고 있었다. 두 라벨의 분기는 **네 상태가 완전히 동일**했다:

| 상단 바 `SpawnTimerLabel` | 텔레그래프 바 `TelegraphTimer` |
|---|---|
| `다음 젠: 대기 중` | `대기 중` |
| `배치 준비 %d초` | `배치 %d초` |
| `마지막 라운드` | `마지막 라운드` |
| `다음 젠: %d초` | `다음 웨이브 %d초` |

둘 다 `ROUND_INTERVAL - round_timer` 에 `ceili`. **같은 숫자, 다른 문구.** 실측으로 동시에 보였다
(`TelegraphTimer="다음 웨이브 15초"` + `SpawnTimerLabel="다음 젠: 15초"`).
**문구가 다르면 플레이어는 서로 다른 타이머로 읽는다** — 정보가 두 배가 아니라 혼란이 두 배다.

고침: **텔레그래프 바가 카운트다운과 예고를 둘 다 소유**한다. "무엇이 오는가"와 "언제 오는가"는
붙어 있어야 한 문장으로 읽힌다. 상단 바는 상태 스트립(`적 N`·`🪙 N G`·8개 버튼)이라 숫자 하나가
거기 있으면 내용과 분리된다. 상단 바 노드 제거 + `@onready` 2개 + `_process` 블록(10줄).

**덤으로 잡은 죽은 표시**: `NextRoundLabel` 은 씬에서 **`visible = false`** 인데 코드가 계속
갱신하고 있었다 — **코드는 보여준다고 믿는데 화면에는 없는** 상태. 예고는 이미
`telegraph_label` 에 나오고 있었으므로 그 노드를 지웠다.

### 프로브를 **고치기 전에** 먼저 돌렸다

## Phase J — 상점 버튼이 사유를 말한다 (§5.2 18 잔여분 = §2.10-c)

§2.10-a(벨트)와 **같은 결함**이 상점에 남아 있었다. 감사는 이 항목에 **전제 조건**을 달아 두었다:
*"문구 서식의 단일 출처를 정한 뒤 손댈 것"*. 그 조건을 **추출이 아니라 가드로** 해소했다(아래).

### 고친 것

```gdscript
# 전 — 사유가 bool 하나로 사라진다. 리터럴 10 이 네 곳(판정·차감·emit·씬 문구).
btn_refresh.disabled = current_gold < 10
btn_buy_relic.disabled = r["sold"] or (current_gold < r["cost"])

# 후 — 벨트(`JamoBelt._button_state`)와 **같은 규칙**: 사유가 곧 판정이다.
const REFRESH_PRICE := 10
func _relic_button_state(r) -> Dictionary:   # sold → '이미 보유한 유물입니다'
                                             # 부족 → '⚠️ 골드가 부족합니다 (필요 %dG · 보유 %dG)'
```

- **순서가 규칙**: `sold` 를 먼저 본다. 사유는 **결정적인 제약**이어야 한다 — 이미 산 유물은
  골드가 아무리 많아도 살 수 없으므로 그 상황의 '골드 부족' 은 **거짓 정보**다(골드를 모으면
  살 수 있다는 뜻이 되므로). 아직 안 산 유물이면 골드가 유일한 제약이라 그걸 말한다.
  (처음 쓴 주석은 "바꿀 수 없는 것부터 말하면 할 일이 없다고 읽는다" 라고 **반대로** 적었다 —
  근거를 '행동 가능성' 이 아니라 '결정적 제약' 으로 바로잡았다.)
- **넣지 않은 것**: '진열할 유물이 없다' 사유. 유물 27종 전부 = **920G**(실측)라 도달 불가.
  분기를 두면 코드만 는다. 그 자리는 `_refresh_button_state()` 주석에 남겼다.
- 씬 문구 `"🔄 갱신 10G"` → `"🔄 갱신"` (가격은 코드가 쓴다 → 네 번째 출처 제거).

### 이번에 새로 당한 함정 넷

1. ⚠️ **`disabled` 는 클릭만 막는다 — `pressed.emit()` 은 통과한다.** 첫 판은 임계 주입(I4)을
   **놓쳤다**: 프로브가 `disabled` 를 존중해 가드 줄을 지나가지 않았다. `_on_refresh_pressed()` 의
   `if current_gold < 9: return` 이 **두 번째 방어선**이고, 그 안의 임계도 상수를 써야 한다.
   → §4b 가 골드 `REFRESH_PRICE-1` 에서 **강제로 눌러** 본다(그 주입이 **-1 G** 를 만들었다).
   **정상 경로로는 원리적으로 보이지 않는 결함**이다.
2. ⚠️ **`queue_free()` 는 지연된다.** `_update_ui()` 가 옛 카드를 지우고 새로 만드는데 같은
   프레임에 세면 옛 버튼이 아직 자식이라 **"카드가 22개다"**(첫 실행 RC=7). 상태 변경 후
   **한 프레임 기다려야** 한다(`await get_tree().process_frame`).
3. ⚠️ **`get_script_constant_map()` 은 인스턴스 메서드다.** 클래스에 직접 부르면
   `Parse Error: Cannot call non-static function … directly`. 인스턴스의 `get_script()` 에서 읽을 것.
4. ⚠️ **프로브에 기대 문구를 적으면 사본이 셋이 된다.** §6 은 두 파일에서 각각 문구를 **추출해
   비교**한다 — 그래서 문구를 **양쪽 다** 바꾸면 안 깨지고 **한쪽만** 바꿀 때만 깨진다.
