> 교훈: 그래픽 드라이버가 걸리면 **프로세스를 죽일 수 없다.** "작업 관리자로 끝내면 되겠지"

## (4) 진단 스크립트 오판 수정 — 로그가 아니라 종료 코드로 판정한다

`check_gpu.sh` 를 다시 돌렸더니 **거짓 초록**이 나왔다:
`✓ 창 생성이 가능한 경로가 있다` (실제로는 전부 크래시).

원인: Godot 의 `CrashHandlerException` 백트레이스가 **1줄만 남을 때가 있다.**
그 실행은 로그에 `Godot Engine v4.7.2...` 한 줄만 있어서 크래시 시그니처 grep 이
실패했고, `[FAIL]` 로 분류되어 크래시 카운트가 2가 됐다 (임계값 3 미만 → 통과).

수정:
1. **종료 코드를 1차 신호로 쓴다.** `rc >= 128` 이면 시그널로 죽은 것 (139 = SIGSEGV).
   모듈 이름 grep 은 '누가 죽였는지' 를 알려주는 용도로만 쓴다.
2. 판정 기준을 바꿨다. **프로젝트를 쓰지 않는 실행(프로젝트 매니저)이 하나라도 죽으면
   프로젝트 코드는 원인이 될 수 없다.** 개수 임계값 대신 이 사실 자체를 판정으로 쓴다.
   → `PM_CRASHES >= 1` 이면 "프로젝트 문제가 아니다" + exit 2.

> 교훈: **로그 내용으로 크래시를 판정하면 안 된다.** 크래시 직후에는 출력이 잘린다.
> 종료 코드는 잘리지 않는다. `run_all.sh` 에서 종료 코드를 보게 고친 것과 같은 교훈이다.

재확인 결과: `pm_opengl3 / pm_d3d12 / pm_vulkan` 3/3 크래시, `headless` 정상,
판정 "프로젝트 문제가 아니다", exit 2. 디스크(C: 491GB 여유)와 `user://` 쓰기도 정상이라
용량 문제는 아니다 (`Can't create shader cache folder` 는 크래시 초기화의 부산물).

## (3) 적 사망 연출 추가 — `EnemyUnit._die()`

감독 지시: **"적 사망에 과정이 생긴거 맞아? 차이를 모르겠는데"**.

**먼저 정정:** (2)에서 나는 사망 연출을 **추가하지 않았다**. "과정이 없다"를 *확인*한 것이고
표 제목이 "확정된 것"이라 오해를 샀다. 감독이 차이를 못 느낀 게 정상이었다.
그래서 이번 턴에 실제로 넣고 before/after 로 증명했다.

### 변경 (`scripts/tower/EnemyUnit.gd`)

`take_damage()` 안에서 `is_dead=true` → `died.emit()` → `queue_free()` 로 끝나던 것을
`_die()` 로 분리, **0.17초 살려 둔 뒤** 지운다.

```gdscript
const DEATH_DURATION: float = 0.17
const DEATH_SQUASH: Vector2 = Vector2(1.32, 0.62)
```

`_die()` 에서 처리한 것과 이유:
- **섬광 트윈을 kill** — `_flash_tween` 을 멤버로 들고 있어야 한다. 안 죽이면 그 트윈이
  매 프레임 `modulate` **전체**를 (1,1,1,1) 로 되돌려 사망 페이드가 매 프레임 취소된다.
  (배너 이중 트윈과 같은 함정)
- `hp_bar.visible = false`, `_attr_badge.visible = false` — 시체에 빈 HP 바가 붙으면
  "HP 0 인데 살아있는" 것처럼 보인다
- `sprite.pivot_offset = sprite.size * 0.5` — TextureRect 기본 피벗이 (0,0) 이라
  그대로 두면 제자리에서 납작해지는 게 아니라 우하단으로 퍼지며 커진다
- **`base := sprite.scale` 을 기준으로** 스쿼시 — 보스는 `BOSS_SPRITE_SCALE` 이라
  `Vector2.ONE` 을 기준으로 잡으면 죽는 순간 원래 크기로 줄어든다
- `died.emit(self)` 는 그대로 — 골드·파편·분열은 전부 `DefenseField` 가 처리하고,
  그 텍스트/파편은 `DefenseField` 의 자식이라 적이 사라져도 살아남는다

### 지연해도 안전한 이유 (설계 근거)

- `DefenseField.get_enemies()` 가 `is_dead` 를 걸러내므로 타워는 즉시 다른 적을 노린다
- `take_damage()` 와 `_process()` 양쪽에 `is_dead` 가드가 이미 있어 시체는 이동도,
  추가 피해도 없다
- `_update_boss_bar()` 도 이미 `is_dead` 를 보므로 보스 HP 바는 즉시 정리된다
- 전체 정리 경로(`get_enemies()` 순회로 free)는 시체를 못 지우지만 0.17초 뒤 스스로
  사라지므로 무해

### 측정 — 도구에 3가지가 필요했다

1. **`slowmo=`** (`Engine.time_scale`). 캡처 루프는 PNG 인코딩 때문에 프레임당 15~45ms.
   0.17초 연출은 실시간으로 **두 프레임 사이에 통째로 숨는다** → "즉시 사라짐"과 구분 불가.
   `slowmo=0.08` 로 0.17초를 약 64프레임에 담았다.
2. **`killat=N`** — N번째 캡처 프레임에서 첫 적을 처치. 타워 사거리 의존을 없애고,
   `follow` 크롭이 앞 프레임에서 위치를 확보한 뒤 죽이므로 시체를 놓치지 않는다.
3. **`dt=`ms** 를 프레임 로그에 추가 — 캡처 주기가 연출 길이보다 긴지 바로 보인다.

### 🔴 로그로는 검증 불가

`field.get_enemies()` 가 `is_dead` 를 걸러내므로 적이 죽는 순간 로그에 `<적 없음>` 이 찍힌다.
**화면에는 시체가 남아 있는데도.** 사망 연출은 반드시 **픽셀로** 세야 한다.
→ 중앙 80×46 박스에서 마지막 프레임(F071) 기준 차이 픽셀 수를 셌다.

| frame | BEFORE (즉시 free) | AFTER (0.17초) |
|---|---|---|
| F005 | 456 | 518 |
| **F006** | **24** ← 한 프레임 소멸 | **470** |

## (4) 감독이 지적한 3건을 실제로 고치고 before/after 로 증명 — HP 바 / 임팩트 / bounce 회전

### 왜 이 섹션이 따로 있는가 (보고 방식 실패)

앞 섹션의 검증 표 제목이 **"✅ 확정된 것"** 이었는데, 감독은 그것을 **"고친 것"** 으로 읽었다.
그 표에 "HP 바가 즉시 튄다 / 임팩트가 없다"가 나란히 있었기 때문이다.
**"검증으로 확인했다"와 "고쳤다"는 완전히 다른 말이다.** 표 제목 하나가 그 둘을 뭉갰다.
→ 감독이 두 번 연속 "이것도 고친거?" 라고 물어야 했다. 앞으로 검증 결과와 수정 결과는
**표를 분리**하고, 수정 보고에는 **같은 조건의 before/after 증거**를 반드시 붙인다.

### (a) HP 바 트레일링 — `Juice.approach()`

`Range.value` 를 **트윈으로 따라가게 하면 안 된다.** 적 HP 바는 초당 수십 번 갱신되고,
갱신마다 트윈을 만들면 같은 프로퍼티에 트윈이 여러 개 붙어 서로 상쇄된다
(`_celebrate_new_words` 에서 이미 밟은 함정). → **프레임 독립 지수 감쇠**를 쓴다.

```gdscript
bar.value = lerpf(bar.value, want, 1.0 - exp(-rate * delta))   # rate 16 ≈ 0.19초에 95%
```

**값을 쓰는 곳을 한 군데로 모으는 것이 핵심.** `EnemyUnit._process` 가 유일한 writer 이고
`take_damage()` / `_tick_regen()` / 화상은 `hp` 만 바꾼다. 적 바·보스 바·기지 바 셋 다 같은 헬퍼.
(`_ready` / `init_enemy` 는 스폰·티어 전환이므로 즉시 대입 유지 — 어차피 같은 값으로 수렴한다)

증거(`slowmo=0.4 hitat=3 hitdamage=9`, HP 26 적):

| frame | BEFORE | AFTER |
|---|---|---|
| `HIT@F003 dealt=9.0` | `hp=17.0` **`bar=17.0`** (같은 프레임 점프) | `hp=17.0` **`bar=26.0`** (아직 안 움직임) |
| F010 | 17.0 | 20.1 |
| F039 | 17.0 (평평) | **17.1** (수렴) |

### (b) 타격 임팩트 — `Juice.impact()` : `ColorRect` → `Sprite2D`

처음엔 `ColorRect` 로 만들었는데 **두 가지가 틀렸다.**
1. 하드엣지 사각형이라 "섬광"이 아니라 UI 사각형으로 보인다.
2. **명중 지점에서 우상단으로 밀려난다** — `Control.global_position` 은 '사각형의 좌상단'이라
   `size/2` 를 빼야 하는데 `pivot_offset` 과 겹치면 어긋난다.

→ **`Sprite2D` + 절차적 라디얼 그라데이션**으로 교체. `Sprite2D` 는 기본이 중심 정렬이라
**위치 계산이 틀릴 여지 자체가 없다.** 텍스처는 `static var` 로 한 번만 만들어 재사용
(분당 100회 넘게 도는데 매번 만들면 그게 부수 비용이다).

```gdscript
static var _flash_tex: GradientTexture2D = null     # GDScript 4 static var
```

**색은 `sprite.modulate` 를 흰색 쪽으로 50% 민 값.** 배경이 초원이라 `bounce` 의 초록
(0.55, 1.0, 0.55)을 그대로 쓰면 배경에 묻힌다. 밝기만 확보하고 색은 남긴다.

크기 튜닝: 처음엔 2.2배(지름 57px)까지 키웠는데 적(36px)보다 커져 "번짐"으로 읽혔다
→ **1.85배(지름 48px), 0.12초**.

증거 — 명중 지점 40×40 박스의 최대 휘도, 같은 조건(`볼` 타워, `slowmo=0.25 fireat=2`):

```

AFTER : F054 219 → F070 194 → F076 182   (단조 감쇠 후 완전 소멸)
LEFTOVER projectiles=0 impacts=0 other=0  (해제 누수 없음)
```

### (c) `bounce` 회전 — 죽은 코드였음

`_apply_trait_appearance()` 가 `bounce` 에 `spin_speed = 9.0` 을 넣어 두었지만
`_process` 의 `sprite.rotation = dir.angle()` 이 매 프레임 덮어썼다.

| frame | BEFORE | AFTER |
|---|---|---|
| F003 | **-2.657** | 0.063 |
| F052 | **-2.657** | 2.363 |

AFTER 는 프레임당 **0.0675 rad** 단조 증가 = `spin_speed(9.0) × delta(0.0075)` 와 정확히 일치.
**효과 크기는 정직하게 "낮음"** — 텍스처 512px × `scale 0.06` = 화면 30px 인데 문양이 4회
대칭이라 회전이 크게 띄지 않는다. "죽은 코드를 살렸다"는 의미가 크고 체감은 작다.

### 🔴 투사체 연출은 `개구리` 로 검증할 수 없다 (한참 헤맸다)

`개구리` 는 `AttackStyle.gd:71` 에서 `trait_id = "orbit"` 으로 해석되고,

→ `Projectile` 이 생성되지 않고 `hit_target()` 이 한 번도 호출되지 않는다.
**피해는 정상적으로 들어가는데 투사체 로그만 전부 비어서 "코드가 안 도는 것"과 구분이 안 된다.**

### 🔴 발사 시점을 운에 맡기면 안 된다 → `fireat=N`

`attack_interval` 이 0.8초라 "발사가 캡처 창에 걸리는가"가 순전히 운이다.

`볼` 은 orbit 이 아니라 실제 사거리 150px 이 필요하다. `at=0.10` 은 적이 438px 밖이었다.

**최근접 적과의 거리 / 사거리내 여부**를 숫자로 찍게 했다. 이제 눈으로 안 헤맨다.
(`diag=1` 은 프레임별 **투사체 위치·회전각**도 찍는다 — 회전은 이미지로 판정 불가다)

### 🔴 테스트가 조용히 썩어 있었다 → `run_all.sh` 가 SCRIPT ERROR 를 실패로 처리

`_update_boss_bar()` 가 `delta` 를 받도록 바뀌었는데 `tests/test_wave_balance.gd` 는
인자 없이 부르고 있었다. `SCRIPT ERROR` 가 찍혔지만 **결과 줄은 `wave balance tests passed`**

채로 남았을 것이다.

- 테스트를 새 계약에 맞게 고침. 이제 **"한 프레임에 점프하지 않는 것" 자체를 검사**한다
  (그게 이번 변경의 핵심이므로).
- `run_all.sh` 의 `run()` 이 **`SCRIPT ERROR` / `Parse Error` 를 실패로 처리**하도록 함.
  결과 줄만 보면 "시그니처가 바뀌었는데 호출부를 안 고쳤다"를 절대 못 잡는다.

## (6) 속성 피해 다양화 요청 — 조사 결과 (구현 전)

디렉터 요청: **"속성 피해의 종류를 더 다양하게 하고 싶어. 적들을 느리게 하는
타워, 체인라이트닝 형식의 공격, 보스전의 특화된 타워, 독타워(HP1로 남음)"**

### 4개 중 2개는 이미 있다

| 요청 | 현재 상태 |
|---|---|
| 느리게 하는 타워 | **이미 있음** — `control` 특성. `slow_factor 0.8` / `1.5초`, 27개 단어(7.4%) |
| 체인라이트닝 | **이미 있음** — `chain` 특성. `_trait_targets()` 로 최대 3마리 동시 타격, 46개 단어(12.6%) |
| 보스전 특화 타워 | **부분 존재** — 보스에 `weakness_trait`(×1.5) / 비약점 ×0.9, 배너에 "약점: X" 표시. 다만 '보스용 타워' 라는 설계는 없음 |
| 독타워 (HP 1로 남음) | **없음** — HP 하한 메커니즘 자체가 없다 (`damage_over_time` 은 화상) |

### 더 큰 발견 — 속성 상호작용 시스템은 이미 깊은데 **전혀 안 보인다**

`EnemyUnit.damage_multiplier_for()` (362-389행) 에 두 축 배율이 이미 있다:

- 타입: 중갑(pierce 1.6 / rapid 0.65 / orbit 0.75 / meteor 1.25),
  군집(splash·bounce·chain·orbit·meteor 1.5 / sniper 0.75), 질풍(control 1.5), 보스(비약점 0.9)
- 속성 `MonsterRoster.ATTR_MULTIPLIERS`: 재생(sniper 1.4/pierce 1.25/meteor 1.3/DoT 0.55/rapid 0.7),
  분열(splash 1.45/chain 1.3/bounce 1.3/meteor 1.35/sniper 0.75), 질주(control 0.5)
- 결계 `warded:<특성>` ×0.35

그런데 이 배율이 **화면에 전혀 표현되지 않는다.** 플레이어는 피해 숫자만 본다.
보스 약점 배너 하나만 예외다. → "속성이 다양하지 않다" 는 체감의 실체는
**다양성 부족이 아니라 가시성 부족** 일 가능성이 크다.

### 뜻↔형태 연결도 절반이 끊겨 있다 (MeaningAudit 실측)

```
전체 366단어
  EXACT(1음절 사전)  11 (3.0%)
  RULES — 단어 자체   57 (15.6%)
  RULES — 설명에서만 111 (30.3%)  ← 플레이어가 예측 불가
  FALLBACK(카테고리) 187 (51.1%)  ← 뜻과 무관한 옛 특성
특성 분포: sniper 85 · orbit 65 · pierce 52 · chain 46 · damage_over_time 35
           · splash 27 · control 27 · meteor 22 · rapid 7(1.9%)
```

`rapid`(연사)가 1.9% 로 가장 희귀하다 — 디렉터가 "연사/폭발/연쇄 아이콘" 을
말한 것과 대조적이다. 아이콘을 붙여도 연사 타워를 거의 못 만난다.

### 특성 이름/설명 테이블

`TRAIT_NAMES`: balanced 균형 · sniper 저격 · damage_over_time 지속 피해 ·
splash **폭발** · rapid **연사** · pierce 관통 · control 제어 · chain **연쇄** ·
bounce 3연속 바운스 · orbit 선회 · meteor 유성  (총 11종)

`TRAIT_DESCS` 는 **orbit / meteor 2종만** 있다 — 나머지 9종은 툴팁에 설명이 없다.

### 디렉터 결정 (질문 답변)

1. **속성 작업 = "표현 먼저"** — 새 특성을 만들기 전에 이미 있는 특성/상성을
   보이게 하는 것부터.
2. **테두리 = 회전 가능/불가능을 통일하고 싶다** — 디렉터는 예전 테두리 색을
   '등급' 이 아니라 **'회전 가능 표시'** 로 읽고 있었다(보라=회전 가능, 슬레이트=불가).
   그리고 그 둘을 통일하길 원한다 → **이미 완료된 변경이 정확히 그 요청**이다.
   → 등급을 새 채널로 되살리는 안은 **하지 않는다**(디렉터가 요청하지 않음).

   실측 확인 (`ab_after.png`, 타일 상단 테두리 y=555):
   ```
   seg2 x281..332 len=52 (76,66,105)   ← ㄷ (회전 불가)
   seg3 x351..402 len=52 (76,66,105)   ← ㅣ (회전 가능)
   seg4 x421..472 len=52 (76,66,105)   ← ㄴ (회전 가능)
   seg5 x491..542 len=52 (76,66,105)   ← ㅗ (회전 가능)
   ```

### 요청 E 1단계 — "표현 먼저" (이번에 구현)
디렉터 결정은 **표현 먼저**. 새 속성을 만들지 않고, 이미 있는 로직 중
**화면에 전혀 드러나지 않던 것** 두 개를 드러냈다.

#### ① 감속(제어) 이 안 보였다 — 제어 타워의 정체성이 통째로 비가시
`apply_slow()` 가 `slow_factor` 만 조용히 바꿨다. 32px 스프라이트의 이동 속도 변화는
플레이 중에 판정이 불가능하다.

**시행착오 (중요):**
1. `sprite.modulate = lerp(white, SLOW_TINT, 0.5)` → **실패**. modulate 는 곱셈이라
   채널을 깎을 뿐이라 초록 적(184,224,128)이 (162,215,128) 로 조금 어두워질 뿐 파래지지 않는다.
2. 같은 텍스처를 물들여 겹치는 `TextureRect` 오버레이 → **작동은 한다**(예측값과 소수점까지 일치:
   184,224,128 → 162,215,128). 하지만 **곱셈이라 똑같은 한계** — 초록은 초록으로 남는다.
3. **정답: `mix` 하는 셰이더.** `shaders/status_tint.gdshader` 를 만들어 `sprite.material` 에 물린다.
   `c.rgb = mix(c.rgb, status_tint.rgb, status_amount * c.a)`
   → 184,224,128 이 (146,210,198) 로 간다. 예측과 정확히 일치. **초록 거북이가 얼음빛 거북이가 된다.**
   `* c.a` 를 곱하는 이유: 투명 가장자리에 색을 섞으면 실루엣이 번진다.
   `sprite.modulate`(피격 섬광)와 안 부딪히는 이유: Godot 은 셰이더 결과 **뒤에** modulate 를 곱한다.

#### ② 감속 '거부'(질주) 도 안 보였다
`slow_immune` 이면 `apply_slow` 가 그냥 `return` — 아무 일도 안 일어난다.
플레이어 입장에서는 제어 타워가 고장난 것과 구분이 안 된다.
→ 이 경우만 '면역' 배지를 띄운다(수명 0.7초, `IMMUNE_BADGE_TIME`).
색으로는 표현할 수 없다(아무 일도 안 일어나니까) 배지가 유일한 수단이다.
배지 위치는 스프라이트 **아래**(`Vector2(-18, 19)`). 좌하단 모서리에 겹쳐 그리면
적 몸통을 가려서 '어떤 적이 면역인지' 를 못 읽는다(실캡처로 확인하고 옮겼다).

#### ③ 상성 배율이 안 보였다 — 표에만 있고 화면에는 없던 숫자
`damage_multiplier_for()` 는 깊은 2축 시스템인데, 배율이 `Projectile`/`Meteor`/`TowerOrbit`
에서 **피해에 미리 곱해져** `take_damage()` 로 들어갔다. 그래서 적은 자기가 약점을
찔렸는지 알 수 없었고, 1.6배와 0.65배가 **똑같이 흰 숫자**로 보였다.

→ `take_damage(amount, show_hit_sound, mult := 1.0, pool_numbers := false)` 로 배율을 함께 넘긴다.
   `_hit_kind()`: mult ≥ 1.35 → `"weak"`(금색 + '약점 ' 접두), mult ≤ 0.72 → `"resist"`(회청색 + '내성 ').
   1.0 근처는 아무 표시 없음 — 매 타격마다 글자가 뜨면 소음이라서.

#### 덤으로 잡은 버그: 선회(orbit) 피해 숫자가 지속피해 색이었다
`take_damage` 의 '숫자 묶기(pool)' 결정이 **'소리 끄기(show_hit_sound=false)' 에 묶여 있었다.**
그래서 소리만 끄려던 `TowerOrbit._hit` 의 타격까지 지속피해 숫자로 묶여 **주황색**으로 나왔다
— 선회는 지속피해가 아닌데도. `pool_numbers` 파라미터로 분리했다
(`_tick_burn` 은 `true`, orbit 은 `false`).
