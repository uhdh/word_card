## Phase K — 한 사건의 흔들림은 **한 방향**이어야 한다 (§2.4-a)

감사 §2.4 문제 2 / §4.5 불일치에 **미해결**로 남아 있던 항목. 문서의 주장은 *"두 흔들림이
서로 다른 위상으로 진행된다 … 따로 노는 느낌이 날 수 있다"* 였고, **재 보니 추측보다 나빴다.**

### 증상

```gdscript
# DefenseField — 보스 등장(:910) / 기지 피격(:1136)
Juice.shake(self, 9.0, 0.35)                  # 필드
Juice.shake(tower_slots_container, 6.0, 0.3)  # $TowerSlots — **self 의 자식**
```

`Juice.shake()` 가 **호출마다 자기만의 RNG** 를 만든다(`Juice.gd:27-28` `rng.randomize()`).
→ 두 노드가 **서로 무관한 방향**으로 흔들린다. 한 사건인데 화면에서는 두 물체가 따로 떨린다.
게다가 자식이라 오프셋이 **합성**된다(자식 화면상 변위 = 부모 + 자기) — 방향이 다르면
합이 상쇄되거나 어긋나서 의도한 '더 세게' 가 '더 흐트러지게' 가 된다.

### 측정 (`tools/ShakeCoherenceProbe.gd`) — 고치기 전

```
SHAKE_PROBE base_hit       frames=20 judged=9  opposed=3 agreement=0.259 worst_angle=81.6deg
SHAKE_PROBE boss_entrance  frames=25 judged=15 opposed=2 agreement=0.569 worst_angle=89.4deg
```

최악 프레임 **82° / 89°** = 사실상 직각. 평균 일치도 **0.26 / 0.57**(한 충격이면 1.0).
**정반대 프레임 3개 / 2개** — 두 물체가 반대로 움직였다.

### 고침

`Juice.shake_together(specs, duration)` 신설 — **같은 오프셋 열**에 각자의 배율만 곱한다.

```gdscript
## ⚠️ RNG 가 **하나**인 것이 이 함수의 존재 이유다.
var unit := Vector2(rng.randf_range(-1.0, 1.0), rng.randf_range(-1.0, 1.0))   # 스텝 루프 안, 노드 루프 밖
for j in range(live.size()):
    (tweens[j] as Tween).tween_property(
        entry["node"], "position", entry["base"] + unit * entry["intensity"] * decay, step_time)
```

- **길이를 하나로** 모았다(보스 0.35/0.3 → 0.35, 기지 피격 0.26/0.22 → 0.26). 한 사건이 두 길이를
  가질 이유가 없다 — 먼저 끝난 노드가 제자리로 돌아가 홀로 멈춘다.
- **WeakRef 되돌림을 `_restore_when_done()` 으로 추출**(두 함수가 같은 패턴을 쓰게 됐다).
  `shake()` 안에만 있던 **죽은 지역변수 `t`**(대입만 되고 안 읽힘)도 지웠다.

### 고친 뒤 — 같은 도구

```
SHAKE_PROBE base_hit       worst_angle=0.0deg agreement=1.000 opposed=0
SHAKE_PROBE boss_entrance  worst_angle=0.0deg agreement=1.000 opposed=0
→ SHAKE_COHERENCE_PROBE_OK (RC=0)
```

### 이번에 새로 배운 것 셋

1. ⚠️ **"함수를 만들었는가" 는 메커니즘이 아니다.** I2 는 `shake_together` 를 그대로 두고
   `unit` 을 스텝 루프 **밖**에서 **안**(노드 루프)으로 옮긴 것뿐이다. RNG 는 여전히 하나지만
   노드마다 뽑으므로 **화면에서는 원래 결함과 똑같다.** §1·§2·§3 이 아니면 통과한다.
2. ⚠️ **지표가 거짓말을 할 수 있다.** `worst_angle` 을 `absf(dot)` 로 계산해서 **정반대(180°)가
   0°** 로 나왔다 — 가장 나쁜 경우가 가장 좋게 보였다. I4 를 §1 만 잡고 §3 이 통과시킨 것으로
   발견했다. `acos(dot)` 그대로 써야 평행 0° · 직각 90° · 정반대 180°.
   **`abs`/`clamp` 로 지표를 만들면 대칭이 되어 방향 정보가 사라진다.**
3. ⚠️ **`EnemyUnit.new()` 로 만든 적은 쓸 수 없다.** `_attach_boss_bar()` 가 `$Sprite`·`$HpBar` 를
   직접 찾아 `Node not found` 2줄을 낸다 — **씬에서 인스턴스된 진짜 적**이어야 한다.
   실제 경로(`start_next_wave()`)로 띄워서 쓸 것.

## Phase L — 단어 완성 배너가 **화면 중앙이 아니었다** (§2.5-a)

감사 §2.5 의 **부수 문제**(우선순위 *최상*·1줄)로 들어갔다. 문서 주장은 *"배너 위치가
`PRESET_CENTER_TOP` + y+40(`JamoBelt.gd:449`)인데 보스 배너(`DefenseField.gd:867`)도 같은
위치라 **두 배너가 겹친다**"* 였다. **재 보니 겹침은 거짓이었고, 대신 다른 결함이 나왔다.**

### 겹침 주장 — ⚪ 철회 (실측)

상단 띠를 실제로 재니 이렇게 나뉘어 있었다(뷰포트 1280×720):

| 요소 | 화면 y |
|---|---|
| 상단 바(`TopBar`) | 0~58 |
| **단어 완성 배너** | 64~86 |
| **보스 체력바** | 76~118 |
| **보스 배너** | 128~170 |

두 **배너**는 42px 떨어져 있다 — 안 겹친다. 감사가 인용한 `:449` · `:867` 은 **다른 개정판의
행 번호**였고(실제는 `JamoBelt.gd:1345` · `DefenseField.gd:938`), `VBox.offset_top = 64` 때문에
보스 배너가 필드 기준 y=54 → **화면 y=128** 이다(문서는 "같은 위치" 라 적었다).

### 진짜 결함 — 주석은 "화면 중앙" 인데 코드는 왼쪽

```gdscript
## 새로 완성된 단어를 화면 중앙에 잠깐 띄워 보여준다.   ← 계약
banner.set_anchors_and_offsets_preset(Control.PRESET_CENTER_TOP)
banner.position += Vector2(-180.0, 64.0)              ← preset 이 **이미** 중앙을 잡았는데 또 -180
```

측정 (`tools/BannerLayoutProbe.tscn`):

| 대상 | 중심 x | 중앙과의 차 |
|---|---|---|
| 단어 1개 | 546.5 | **93.5px 왼쪽** |
| 단어 3개 | 460.0 | **180.0px 왼쪽** |
| 보스 배너 (비교) | 640.0 | 0.0px |

⚠️ **1개와 3개가 왜 다른가** — preset 은 `custom_minimum_size`(360) 가 아니라 **그 시점의 글자
최소폭**으로 크기를 잡는다(실측 187 / 385). 즉 **최소크기 캐시가 낡아** `custom_minimum_size` 가
반영되지 않았고, 그래서 폭이 글자 길이를 따라가 밀리는 양까지 달라졌다.
→ **짧은 단어만 재면 결함의 절반만 보인다**(그래서 프로브 §5 가 긴 단어를 따로 잰다).

같은 파일 `:1340` 의 주석 "보스 배너와 같은 관례를 쓴다" 도 **거짓**이었다 — 보스 배너는
`position = Vector2(-160.0, 54.0)` 으로 `=`(앵커 기준 절대값)를 주므로 정확히 중앙이다.
**두 배너의 관례가 서로 달랐던 것이 원인.**

### 고침

```gdscript
banner.set_anchors_and_offsets_preset(Control.PRESET_TOP_WIDE)   # 폭을 앵커에 맡긴다
banner.position.y = 64.0
banner.pivot_offset = banner.size * 0.5                          # 세로 pivot 도 0 이었다
```

- `custom_minimum_size = Vector2(360, 0)` 과 그 주석은 **삭제** — 폭이 앵커에서 나오므로 무의미하고,
  "preset 보다 먼저 정해야 폭이 잡힌다" 는 설명이 **거짓**이었다(그래서 이 결함이 생겼다).
- **pivot**: 전엔 `custom_minimum_size * 0.5` = `(180, 0)` → 세로 pivot 이 **0** 이라 BACK_OUT 팝이
  가운데가 아니라 **위쪽 모서리**에서 자랐다(실측 `(180,0)` vs 중심 `(180,11)`). 주석이 요구한 것을
  코드가 안 지키고 있었다.
- ⚠️ **감사 §6.2-3 이 정반대 처방을 적어 두고 있다**(`size * 0.5` → `custom_minimum_size * 0.5`).
  그건 `PRESET_TOP_WIDE` 이전의 이야기라 **지금은 `size * 0.5` 가 맞다** — 코드 주석에 "이 줄을
  되돌리지 말 것" 이라고 근거와 함께 적었다.

   프로브는 `horizontal_alignment` 회귀를 **못 잡는다**. 정렬 속성을 함께 단언해야 한다(§2b).

## Phase M — 붉은 섬광이 **두 곳에 복사**돼 있었고, 설명은 "전체 화면" 이었다 (§2.11-a)

§2.11 의 **부수 문제**(§5.2 15 의 나머지 — Phase L 에서 "아직 안 했다" 로 남겨 둔 것). 문서 주장은
*"보스 등장과 기지 피격의 붉은 섬광 8줄이 동일하다"* 였다. **맞았고, 대신 그 8줄의 주석이 거짓이었다.**

### 증상 — 숫자만 다른 같은 8줄

```gdscript
# DefenseField.gd:918 (보스 등장) / :1149 (기지 피격)
var rect := ColorRect.new()
rect.color = Color(Palette.HP_DANGER.r, Palette.HP_DANGER.g, Palette.HP_DANGER.b, 0.0)
rect.mouse_filter = Control.MOUSE_FILTER_IGNORE
rect.set_anchors_and_offsets_preset(Control.PRESET_FULL_RECT)
add_child(rect)
var tw := rect.create_tween()
tw.tween_property(rect, "color:a", 0.22, 0.12)   ← 이 세 숫자만 다름 (0.18 / 0.08)
tw.tween_property(rect, "color:a", 0.0, 0.5)     ← (0.28)
tw.tween_callback(rect.queue_free)
```

### ⚠️ 주석·감사가 함께 틀렸다 — "전체 화면 붉은 비네트"

`_juice_base_hit()` 의 docstring 은 `## 전체 화면 붉은 비네트` 였고 감사 §2.11 도 그대로 옮겨 적었다.
**재 보니 전체 화면이 아니다:**

```
FLASH OPEN_ITEM coverage=48.3% of screen (field only, flat plate)
```

`PRESET_FULL_RECT` 의 부모가 `DefenseField`(= `FieldContainer`, 1248×384)라 **필드만** 덮는다.
비네트(가장자리 감쇠)도 아니고 **단색 판**이다. 즉 설명이 두 번(주석·감사) 틀렸다.

### 고침 — `Juice.flash()`

```gdscript
static func flash(parent: Control, color: Color, peak: float, fade_in: float, fade_out: float) -> void
```

- **이름을 `flash_screen` 으로 짓지 않았다.** 감사가 그렇게 제안했지만 범위가 화면이 아니라 필드다 —
  이름에 `screen` 을 넣으면 **틀린 계약이 API 에 새겨진다**(§2.4-a·§2.10-c 와 같은 함정).
- **알파를 항상 0 에서 시작하도록 강제**한다. 트윈은 '현재 → 목표' 로 보간하므로 호출자가 `a=1` 색을
  넘기면 섬광이 **꺼지는 것부터** 시작한다.
- docstring 에 계약(부모를 채운다 · 마우스를 먹지 않는다 · 스스로 사라진다)과 **왜 이 함수가 있는지**
  (8줄 복사)를 적었다. `DefenseField` 두 곳은 각각 한 줄이 됐고 `_juice_base_hit` 의 거짓 문구는
  `붉은 섬광 1회` + ⚠️ 블록(48.3% · 단색 판 · 고칠 방향은 감독 결정)으로 바꿨다.

### ⚠️ 순수 리팩터의 프로브는 **고치기 전에도 통과한다** — 근거는 '숫자가 같다' 이다

동작이 변하면 안 되는 변경이라 "깨진 코드에 먼저 돌려 보기" 가 성립하지 않는다. 대신 **pre-edit 파일을
복원해 만든 '전' 수치**와 '후' 수치가 같음을 보인다:


## Phase N — 남은 주사위가 **화면에 없었다** (§2.14 신규)

§2.13-1(카운트다운 중복)을 정리한 뒤 **같은 부류를 한 번 더 찾아보았다.** "한 채널을 두 곳에서

## Phase Q — 감사 문서 **신선도 점검** (감사 §0.3 신설)

### ⚠️ 이번 점검의 핵심 교훈 — **"그 grep 을 다시 돌려 보는" 방식은 못 잡는다**

**§2.3 이 결정적이다.** 감사는 "`tween_property(..., "value", ...)` 가 0건이다. 전부 즉시
대입이다" 라고 썼다. **그 문장은 지금도 참이다** — 여전히 0건이다. 그런데 **HP 바는 고쳐졌다.**
고침이 **트윈을 안 쓰고 지수 감쇠**를 썼기 때문이다(`Juice.approach`). 즉:

- **감사의 '근거 문장' 을 재검증해도 '결론' 의 낡음은 못 잡는다.**
- **§2.7 은 제목·본문 양쪽이 침묵**해서, 문서 안의 표식만 훑는 자동 점검은 "변화 없음" 으로 지나간다.
- → **코드를 읽고 원래 주장을 다시 재는 것 말고는 방법이 없다.** 점검 스크립트로 대체 불가.

`Juice.approach()` 주석이 **왜 트윈이 아닌지**까지 적어 두었다(그대로 인용할 가치가 있다):
1. 적 HP 바는 **초당 수십 번** 갱신된다 → 갱신마다 트윈을 만들면 **같은 프로퍼티에 트윈이 여러 개
   붙어 서로 상쇄**된다("이 프로젝트에서 반복적으로 밟은 함정").
2. **프레임 독립 지수 감쇠**라 **4배속에서도 체감이 같다.** 트윈은 `time_scale` 을 타므로 배속마다
   따라붙는 속도가 달라진다 — §2.11 의 "3초 → 0.77초" 사고와 **같은 뿌리**다.

또 **감사의 제안과 실제 고침이 다르다**: 제안은 "트레일 바 1겹 추가 + 0.15/0.35/0.30초 차등" 이었고,
실제는 **바 하나를 같은 `rate=16`(≈0.19초에 95%)으로 감쇠**시켰다. 차등은 채택되지 않았다.

## Phase S — §2.14 재판정: 감사의 결론이 틀렸다 (2026-09-24, 감독 선택)

감독이 "§2.14 재판정" 을 골랐다. 결과적으로 **감사의 미해결 항목 하나가 거짓**이었고, 그 거짓을
**내 프로브가 퍼뜨리고 있었다.**

### 발견 — "툴팁은 화면이 아니다" 는 틀렸다

감사 §2.14 의 「남긴 것」:

> ⚠️ 잔량을 보여주는 곳이 툴팁 하나뿐이다. … 즉 플레이어는 리롤할 생각을 이미 한 뒤에야 잔량을 안다.

실측은 반대다:

| 채널 | 어디 | 언제 | 실측 |
|---|---|---|---|
| `WaveRewardModal` 의 `DiceLabel` | `RerollRow` — **리롤 버튼과 같은 줄** | 모달이 떠 있는 동안 항상 | `is_visible_in_tree()=true` · `"남은 주사위 2개"` |

### 왜 틀렸나 — 채널 하나를 재고 '화면 전체' 를 판정했다

`DiceVisibilityProbe` 는 **툴팁만** 재는 도구였고, §6 이 "보여주는 곳이 툴팁 하나뿐" 이라고 **보고**했다.

여기서는 근거가 참인데 **주장의 범위**가 넓어져 틀렸다.
⚠️ **한 채널을 측정한 결과로 "화면에 없다" 고 말하면 안 된다.**

## Phase U — 자기 오류 발견·정정: "함수 하나를 재고 메커니즘 전체를 판정" (2026-09-24)

감독이 "그 다음은?" 이라 물어 §2.8/§5.2 10(승리·패배 연출)을 파다가, **Phase T 에서 내가 쓴 §3
정정 3행이 틀렸다**는 것을 발견했다.

### 무엇을 틀렸나

Phase T 에서 §3 의 `결과 화면`·`Victory`·`Game Over` 행에 이렇게 적었다:

> 패널 자체는 **여전히 즉시 등장**(등장 트윈 없음). … 패널 등장 트윈은 아직 없다.

**틀렸다.** `_on_game_over()` 본문(1334~1505)만 grep 해서 `tween`·`scale`·`modulate` 가 0건인 것을
보고 그렇게 썼는데, 연출은 **그 함수가 호출하는 `_show_modal()`(`:965`)** 안에 있었다:

```
panel.pivot_offset = pivot
panel.modulate.a = 0.0
panel.scale = Vector2(0.92, 0.92)
var tw := create_tween().set_parallel(true)
tw.set_trans(Tween.TRANS_BACK).set_ease(Tween.EASE_OUT)
tw.tween_property(panel, "modulate:a", 1.0, 0.18)
tw.tween_property(panel, "scale", Vector2.ONE, 0.18)
```

`_show_modal` 은 모달 6곳이 전부 타는 공용 함수이고(호출부 `:276`·`:554`·`:960`·`:1100`·`:1261`·
**`:1499`=게임오버**), **이미 있던 연출을 "없다" 고 적을 뻔했다.**

### ⚠️ 더 나쁜 것 — §5.2 10 은 처음부터 맞게 적고 있었다

`§5.2 10` 은 원래 **"BACK_OUT 은 이미 있음"** 이라고 적고 있었다. 즉 **§3 과 §5.2 는 원래 모순**
이었는데, 점검이 그 모순을 **해소하는 대신 반대편으로 키웠다.** §4.2 vs §3 에서 찾은 것과
**정확히 같은 종류의 모순을, 같은 점검 안에서 재생산**한 것이다.

### 왜 이게 §2.14 와 같은 부류인가

Phase S 의 §2.14 도 **"툴팁 채널 하나만 재고 '화면 전체' 를 판정"** 한 결론이었다.
이번엔 **함수 하나만 재고 '패널의 등장' 을 판정**했다. **같은 오류를 같은 세션에서 두 번** 냈다.

**규칙 둘:**
1. **함수 하나를 재고 메커니즘 전체를 판정하지 마라.** 연출은 이벤트 핸들러가 아니라 **호출되는
   공용 함수**에 있는 경우가 많다 → **호출 그래프를 따라가라.**
2. **점검자도 자기 규칙을 어긴다.** "없다" 를 주장할 때는 **그 주장이 미치는 범위를 먼저 세라.**

### 정정 내역

- **§3** `결과 화면`·`Victory`·`Game Over` 3행 → BACK_OUT 등장이 **이미 있다**로 정정.
- **§5.2 10** 에 `_show_modal()` 상호 참조 + "§3 의 '정적 패널' 은 이 행과 모순이었다" 명시.
- **§0.3** 에 「⚠️ 이 점검 자체가 낸 오류」 소절 신설(위 규칙 둘 포함).
- 감사 2,733 → **2,754줄**.

### 결과 — 남은 것은 '여운' 하나뿐

승리·함락의 연출은 **전용음 + BACK_OUT 등장**이 이미 있다. 빠진 것은 **등장 뒤 0.4초 정적
(§5.2 10 ⏳)** 하나다. 즉 이 항목은 "연출이 없다" 가 아니라 **"여운이 없다"** 이다.
⚠️ 그러므로 **결과 패널에 등장 연출을 새로 넣는 일은 하면 안 된다** — 이미 있다.

### 인수

- 코드 **무변경**(문서만). Phase S 의 `REAL_RC=0` 유지(이후 코드 변경 없음).
