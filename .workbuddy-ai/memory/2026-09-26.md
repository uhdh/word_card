# 2026-09-26 — Phase W: 보스 약점은 규칙인데 전투 중에 화면에 없다

## 무엇을 했나

지난 페이즈(V)의 네 항목을 마감한 뒤, 감독 지시("이제 뭐해야해?")에 대한 답으로
**다음 후보를 찾는 정찰**을 했다. 결과는 **새 발견 하나** — 감사에 없는 항목이다.

### 발견 — `BossWeaknessProbe` (신규, `tools/`)

`scripts/tower/DefenseField.gd:926` 의 함수 머리말은 이렇게 약속한다:

> ## 보스 등장 배너. 약점을 함께 알려줘서 '무엇으로 때려야 하는지' 를 **즉시 전달한다.**

그리고 `scripts/tower/MonsterRoster.gd:61` 은 보스에게 **타입 배지를 달지 않는 이유**를 적는다:

> ## 'boss' 도 배지를 달지 않는다: 보스는 등장 배너가 약점까지 크게 알려 준다.

즉 **배너가 약점의 유일한 '등장 시점' 채널**이다. 그 배너는 트윈으로 떴다 사라진다.
그러면 질문이 남는다 — **배너가 사라진 뒤, 보스가 아직 살아 있는 동안 그 규칙은 화면 어디에 있는가.**

실측(`tools/BossWeaknessProbe.tscn`, RC=0 · `BOSS_WEAKNESS_PROBE_OK`):

| 재는 것 | 실측값 |
|---|---|
| 약점의 무게 — 약점 vs 비약점 배율 | **1.50 vs 0.90 = 1.67배** |
| 등장 전 예고 (`next_round_preview`) | ✓ "…보스 · **약점 관통** \| …" |
| 그 부분이 잘리는가 | **아니다** — 접두 189px / 라벨 1162px |
| 전체 예고 폭 | 1154px vs 라벨 1162px → **계획 중엔 다 들어간다** |
| 등장 순간 배너 | ✓ `["약점: 관통"]` 1건 |
| 배너 수명 @1배속 | 게임시간 **2.15s** / 실시간 2.10s |
| 배너 수명 @4배속 | 게임시간 2.22s / 실시간 **0.56s (게임시간의 25%)** |
| **배너가 사라진 뒤 보이는 '약점' 문구** | **0건** (보스는 생존 중) |
| 그동안 남아 있는 것 | 보스 체력바 (보임, 행 2개 = 이름+체력, 약점 언급 **없음**) |
| 비약점 타격의 피해 숫자 분류 | **`normal`** — 표시 없음 |

**핵심**: 약점은 1.67배 규칙이고, 웨이브 전 예고 + 등장 배너 **두 번** 알려준다.
그런데 **보스와 싸우는 동안**에는 화면에 없다. 4배속이면 배너가 **0.56초**만 보인다.
그리고 전투 내내 남는 유일한 요소(보스 체력바)는 약점을 말하지 않는다.
결정적으로 **틀린 특성으로 때리면 피해 숫자가 평범한 흰색**이다 — 비약점 배율 0.90 이
내성 임계(`RESIST_MULT=0.72`)보다 **위**라서 '내성' 라벨이 안 붙는다(`_hit_kind`).
즉 플레이어는 **시행착오로도** 알 수 없다(맞는 타워를 이미 가진 사람만 '약점' 라벨을 본다).

### ⚠️ 감사에 이 항목이 없었던 이유

§2.4 문제 4 는 "예고(Anticipation)가 없다"(보스가 이미 걸어오는 중에 연출이 터진다)였고,
§5.3 25 는 "게임 진행을 멈춰야 함" 이라 보류됐다. **둘 다 '등장 전' 이야기**다.
여기서 잰 것은 **등장 후** — 다른 질문이고, 문서 어디에도 없었다.

### ⚠️ 재지 않은 것 / 주장하지 않는 것

- **"플레이어가 약점을 모른다" 고 주장하지 않는다.** 정보는 두 번 나온다(예고 + 배너).
  잰 것은 "배너가 사라진 뒤에도 남아 있는가" 다.
- **이건 결함인가 설계인가 — 감독 판단이다.** "기억하게 하는 것" 이 의도일 수 있다.
  그래서 고치지 않고 **측정 + 선택지**로 멈췄다.
- **체감은 미검증**(헤드리스). 배너를 놓치는 빈도는 사람이 해봐야 안다.

### 시도했다가 **소진**한 방법 — 딕셔너리 키 스캔

`ATTR_INFO.desc` 를 찾아낸 방법을 기계화했다: 각 `const NAME = {…}` 의 키 중 **그 상수를
통해서는 한 번도 읽히지 않는 키**를 전수로 뽑기. 정밀화 판본(`dictscan2.py`)은
**정적 접근(`DICT["리터럴"]`)과 동적 접근(`DICT[변수]`)을 갈라** 동적이면 배제한다.

**결과: A 목록이 비었다 — 그리고 그것이 정답이다.** 살아 있는 `scripts/` 의 const 딕셔너리
**21개가 전부** 동적 인덱싱이거나 통째로 전달된다(`ATTR_INFO.get(attr_id,{})` · `NAMES.get(trait_id,…)` ·
`TYPE_MULTIPLIERS[text]`). 즉 **이 스캔은 이 코드베이스에서 원리적으로 발견을 낼 수 없다.**
→ **`ATTR_INFO.desc` 는 이 방법으로 찾힌 게 아니었다**(소비자 수를 세는 다른 방법이었다).
⚠️ **A 가 비었을 때 "찾을 게 없다" 로 읽으면 안 된다** — *"이 도구가 못 본다"* 와
*"없다"* 는 다르다. 그래서 진단 표(D)로 21개가 각각 왜 배제됐는지 세어 **공허성**을 확인했다.

## (8차) §2.23 — 기지 피격이 적 피격과 **같은 소리**다 · 그리고 **삼켜질 수 있다** (2026-09-26)

### 발견 경로 — §2.22 의 교훈을 기계화했다
§2.22 는 *"손으로 고른 목록이 틀린다"* 였다. 그래서 이번엔 **질문을 좁히지 않고 전수**로 갔다 —
`scripts/` 전체의 `SoundEngine.play_*` 호출처 **50곳**을 `soundcensus.py` 로 뽑아 함수별로 귀속시켰다.
`play_tile_combine`(타일 교체)은 확인 후 보류했고, 대신 **`play_hit` 이 두 곳**에서 같은 이름으로
불리는 것을 발견했다 — `EnemyUnit.gd:591`(적 피격) · `DefenseField.gd:1126`(기지 피격).

### 왜 이것이 "로직은 있는데 표현이 부족한 사건" 인가
`DefenseField.gd:1127` 의 주석이 **스스로 등급을 적어 두었다** —
`# 기지 피격은 가장 강한 타격감이 필요한 순간 → 화면 흔들림 + 붉은 플래시`.
그런데 `_juice_base_hit()`(`:1143`)은 **시각 전용**이고 `SoundEngine` 호출이 **0건**이다.
소리는 바로 위 `:1126` 의 `play_hit()` 하나뿐 — **적 피격과 같은 이름** → **같은 파형**, 귀 구별 불가.

### 실측 (BaseHitSignalProbe · 7섹션 · RC=0)
```
BASE_HIT base_hit_calls=["play_hit"] enemy_hit_calls=["play_hit"]
BASE_HIT juice_base_hit_calls=[] low_hp_warning_calls=[]
BASE_HIT base_hit_solo_plays=["hit"]
BASE_HIT collision before=8 after_enemy_hit=9 after_base_hit=9
BASE_HIT three_arrivals before=9 after=10
BASE_HIT hit_duration=0.12 rank=3/17 shortest5=[0.05, 0.08, 0.12, 0.12, 0.16]
BASE_HIT contract noise_ban=[".../TowerDefenseMain.gd"] player_text=[]
```

### 핵심 — 우선순위 역전
`_play_synth_stream()` 의 스로틀은 **이름별**(`_last_played_msec[stream_name]`, `SFX_MIN_INTERVAL_MSEC := 50`).
같은 프레임에 적 피격 → 기지 피격이 오면 **기지 피격음이 삼켜진다**(`+0`). 한 프레임에 여러 번
요청하는 경로가 실재한다(`Meteor._impact()` 가 폭발 반경의 적을 전부 순회) → 가설이 아니다.

측정을 **비공허**하게 만든 장치 셋 — 이게 이번 절의 방법론이다:
1. **양성 대조** — 같은 프레임에 **다른 이름**(`coin`)은 **+1**. 그래야 "안 늘었다" 가 의미를 갖는다.
2. **풀 포화 가드** — `before <= _players.size() - 3`. 12개가 다 재생 중이면 `_get_player()` 가
   `_players[0]` 을 주고 재-`play()` 가 수를 안 올린다(**거짓 통과**).
3. **`_last_played_msec` 으로 세지 않았다** — 그 딕셔너리는 **덮어쓴다**(몇 번 났는지 못 센다).
   `p.is_playing()` 을 셌다.

### '결함' 이 아니라 '결정 대기' 로 분류한 이유
`TowerDefenseMain.gd:595` 에 감독의 원칙이 적혀 있다 — **`소음 금지`**.
그래서 확실한 것은 셋뿐이라고 적었다: ① 지금은 귀로 구별할 수 없다 ② 삼켜질 수 있다
③ 코드가 이 순간을 *"가장 강한 타격감"* 이라 적어 두었다. **권장 B(삼켜짐만 고침 — 새 소리 0·새 효과 0).**
⚠️ **원칙이 적혀 있는 자리에서는 측정이 곧 판정이 아니다** — 이번 판에서 처음 만난 형태다.

## (9차) §2.22 (§5.2 34) — 소리의 **배치**를 바로잡았다 · 감독 선택 **(C) 재배치** (2026-09-26)

### 먼저 — "C안" 이 둘이었다
앞선 보고에서 내가 **C** 를 두 곳에 권장했다: **§2.22 34-C**(재배치) 와 **§2.24 36-C**(벨트 라벨).

### 고침의 정의 — 셈이 아니라 **배치**
§2.22 는 *"`play_buff` 의 호출처가 3곳인데 감사가 0건이라 했다"* 로 시작했지만, 실은 **개수**가 문제가
아니었다. 세 호출처는 **성격이 다른 세 사건**이었고 그중 둘에 **'좋은 일' 파형**이 붙어 있었다:

|---|---|---|---|
| 유물 구매 (`ShopModal.gd:279`) | `play_buff` | **`play_buff` 유지** | 이름이 맞다 — 유물은 *지속되는* 이득. 이제 이 소리의 **유일한 주인** |
