## 요청 F — 선회(orbit) 방향을 시계/반시계로 바꾸는 기능 (구현·검증 완료)

감독 요청: "선회의 방향을 시계, 시계 반대로 바꾸는 기능을 넣어줘"

### 핵심 발견 — 방향은 연출이 아니라 배치다
- 궤도 오브는 반지름 76px 를 2.6초에 한 바퀴 → 183.6 px/s. 판정 지름 46px
  (HIT_RADIUS 15 + HIT_SLACK 8, ×2).
- 적이 60px/s 로 지나갈 때, 오브가 적과 **같은 쪽**으로 돌면 상대속도 123.7 이라
  접촉 0.37초 → 재타격 대기 0.3초를 넘겨 **2대**. 마주 돌면 243.7 이라 0.19초 → **1대**.
- 즉 **같은 자리에서 만나도 방향만으로 피해가 2배**다. 실측으로 확인함.
- 그리고 **유리한 방향은 적이 궤도의 어느 쪽으로 지나가는지에 따라 뒤집힌다**
  (아래로 지나가면 반시계, 위로 지나가면 시계). 그래서 전역 스위치가 아니라
  타워마다 골라야 한다는 결론. → per-tower 로 구현.

### Godot 사실 — 2D 는 y 축이 아래라 '각도 증가 = 화면상 시계 방향'
`Vector2.RIGHT.rotated(a)`: a=0 → 3시, a=π/2 → 6시(y 아래). 즉 각도가 커지는 쪽이
화면에서는 **시계**다. 예전 코드(`_angle +=`)는 시계 방향으로 고정돼 있었다.
(요약본에 "반시계로 고정" 이라고 적혀 있었는데 그건 화면 기준으로 틀린 서술이었다.)

   - `_draw` 의 책 넘김(`_angle * 3.0`)도 방향에 맞춰 부호를 뒤집는다.
     궤도만 뒤집으면 책이 따로 노는 것처럼 보여 전환이 읽히지 않는다.
   - 뒤집을 때 `_angle` 은 유지 → 오브가 제자리에서 부드럽게 돈다(순간이동 없음).

### 설계 결정 — '적용' 과 '기억' 을 분리
처음엔 `DefenseField.set_tower_orbit_direction(slot, cw)` 가 `active_towers` 를 뒤져
적용하게 했는데, 테스트에서 타워가 목록에 없자 **클릭이 조용히 씹혔다**.

'이 슬롯은 이 방향' 이라고 알린다(`remember_orbit_direction`).
필드에만 맡기면 목록에서 못 찾는 순간 무반응, 필드를 빼면 자모 수정 시 선택이 사라진다.

## 요청 G — 단어 조합 힌트를 Wordle 방식으로 (아이데이션만, 구현 전)

감독 요청: "단어 조합 힌트를 주는 방식을 변경하고 싶어. wordle처럼 주고 싶은데,
방법을 아이데이션 해보자"

### 현재 힌트 (사실 정리)
- `JamoBelt` 헤더의 "초성 힌트" 버튼 → `WordSynergy.initial_hint(belt, words, hint_index, reveal)`
- 벨트로 만들 수 있는 단어 중 **가장 긴 것만** 남기고, `hint_index` 로 순환하며
  **초성만** 보여 준다. `relic_initial_compass`(훈민정음의 나침반) 를 사면 완성 단어까지.
- 출력은 `PreviewLabel` — "자동 완성 타워: …" 와 **같은 한 줄**을 덮어쓴다. `clip_text = true`.

### 현재 힌트의 문제 (아이데이션 근거)
1. 추리가 아니라 **조회**다. 한 번 누르면 끝 — 되돌아올 이유가 없다.
2. **초성은 가장 쓸모없는 조각**이다. "ㄱㄴ" 만 주고 중성·종성은 피드백 없이 맞히라 한다.
3. **가장 긴 후보만** 보여 준다. 1음절 orbit/meteor 처럼 짧지만 강한 선택지가 안 보인다.
4. `hint_index` 로 순환하지만 "2번째 / 5개" 같은 표시가 없어 무작위처럼 느껴진다.
5. **배치**를 전혀 돕지 않는다 — 그런데 플레이어가 실제로 막히는 지점이 배치다.
6. 한 줄 라벨을 덮어써서 더 풍부한 것을 넣을 자리가 없다.

### Wordle 에서 가져올 것은 색이 아니라 '추리 구조'
- Wordle 글자 → **자모 슬롯**(초성/중성/종성 자리), 위치 → **단어 안의 자리**
- 🟩 자리 맞음 / 🟨 단어엔 있지만 다른 자리 / ⬛ 이 단어엔 안 씀
- 추측 → **플레이어의 현재 벨트 배치**
- **비밀이 무엇이냐**가 설계의 갈림길이다.

### 후보안 4개 (감독 선택 대기)
1. **벨트 채점** (추천) — 힌트가 정답 대신 채점표를 준다. 목표 단어 하나를 골라
   벨트 타일에 🟩/🟨/⬛ + 부족한 활자 표시. 새 화면 없음.
   `AutoArrange._tiles_for_word(word, owned)` 가 이미 '정답지'를 돌려준다.
2. **추리 보드** — 별도 격자에 시도가 쌓이고 숨은 단어를 맞히면 보상. 진짜 Wordle.
   단, 신규 콘텐츠(막별 비밀 단어·보상·저장)이고 방어라는 본 목표와 경쟁한다.
3. **목표를 플레이어가 고른다** — 도감/조합 추천에서 단어를 고르면 그 기준으로 채점.
   추리가 아니라 제작 체크리스트.
4. **3단 사다리** — 무료(몇 자리 맞는지) / 골드(틀린 자리 하나) / 나침반(단어 공개).

### 감독 결정 (2026-09-20) — 1안 '벨트 채점' 으로 진행
감독이 던진 두 질문이 설계를 확정했다:
- "현재 만들 수 있는 최고로 좋은 단어를 목표로 하는거지?" → **맞다. 단 '그 슬롯의 타일로'
  만들 수 있는 최선**이어야 한다 (벨트 전체 최적이 아니라).
- "슬롯이 3개인데, 1개 골라서 해야하지 않을까?" → **맞다. 그리고 이미 슬롯이 행이다.**

#### 확정된 사실 — 게임은 일부러 배치를 대신 해 주지 않는다
`JamoBelt.optimize_tiles()` 는 `strategy_recommendations_requested` 만 emit 하고
`slot_assignments` 는 건드리지 않는다. `test_tower_traits.gd` 에 이를 강제하는
테스트가 있다: `"Recommendations must not place tiles for the player"`.
→ 즉 **배치는 플레이어의 일로 설계돼 있다.** 그래서 배치 힌트는 조합 추천과 중복이
아니라 **비어 있는 자리**다. (조합 추천 모달은 '가능한 단어 목록'만 텍스트로 준다.)

#### 확정된 사실 — 벨트는 이미 슬롯별 행 구조다
`render_belt()` → `_add_tile_group()` 이 슬롯마다 `JamoTray` 를 하나씩 만든다:
제목 "1번 슬롯" / "2번 슬롯" / "3번 슬롯" / "대기 타일", 각 트레이 안에 HBoxContainer
한 줄. 즉 **Wordle 행을 위한 새 레이아웃이 필요 없다** — 각 트레이 안 타일에 색을
입히면 그게 곧 그 슬롯의 채점 행이다.

#### 확정된 설계
- 목표 = 그 슬롯 타일로 만들 수 있는 최고 점수 단어.
  점수 정의는 이미 있다: `AutoArrange._word_score` = `tier × 1000 + damage`
  (+ 프로필별 카테고리 보너스 700).
- 색: 🟩 자리 맞음 / 🟨 이 단어엔 있지만 다른 자리 / ⬛ 이 단어엔 안 씀(빼라)
  / ⬜ 아직 없는 자리(점선).
- 슬롯 타일로 단어를 **아예 못 만들면** 목표가 없다 → 결손이 가장 적은 단어를 목표로
  잡고 부족한 활자만 보여준다. ("ㅓ 하나만 더 있으면 얼음")
- 대기 타일 트레이도 채점 대상: 어떤 슬롯의 목표에 필요한 타일이면 표시해서
  "이걸 1번 슬롯으로 끌어와라" 를 알려 준다.
- 세 슬롯을 **한꺼번에** 채점한다(1개 고르기가 아니라). 세 슬롯은 타일을 나눠 쓰므로
  한 슬롯만 보면 나머지에 무엇이 남는지 알 수 없고, 이미 세 줄이 세로로 쌓여 있다.

#### 남은 갈림길 — 나침반 유물
`relic_initial_compass`("훈민정음의 나침반")의 현재 효과는 "힌트가 초성 대신 완성
단어를 알려줍니다" 다. 새 방식은 목표 단어를 다루므로 이 유물과 겹친다.
(a) 무료=색만 / 나침반=목표 단어 이름까지 (기존 사다리 유지)
(b) 무료=목표 이름까지 / 나침반=자리까지 정확히
(c) 나침반 효과를 다른 것으로 교체
→ 감독 선택 대기. 참고: 부족한 활자를 보여주면 목표 단어가 거의 유추되므로
  (ㅂㅓㄴ + "ㄱㅏㅣ 부족" → 번개) (a)와 '부족한 활자 공개'는 서로 당긴다.

### 참고 — 이미 있는 것
- `AutoArrange._tiles_for_word` = 특정 단어를 내 타일로 만들 수 있는지 + **어느 타일이
  어느 자모 슬롯을 채우는지**까지 돌려준다. Wordle 채점의 재료가 이미 있다.
- `AutoArrange.buildable_words_for` / `best_word_set_for` / `strategic_sets_for`
- "조합 추천" 버튼 → `_on_strategy_recommendations_requested` → 가능한 단어를
  **텍스트 줄 목록**으로 보여 주는 모달. 즉 배치는 게임이 이미 풀어 준다.
- 단어 189개 (`WordDatabase.WORD_DATABASE`). `LexiconModal` 에 도감/해금/검색이 있다.
- 자모 타일은 **회전** 가능하고 **겹자음(ㄲ 등)·겹모음(ㅘ 등)** 타일이 있다.
  → 한 자모 슬롯을 여러 타일로 채울 수 있다(조합 사전 `CONSONANT_COMBINATIONS`).

타일 단위 상태를 합친다.

### 고정(lock)
- `slot_targets` / `slot_locked` / `slot_reserved` / `slot_lock_order` 네 개가 상태.
- 힌트를 안 눌렀으면 **지금 슬롯에 완성된 단어**를 고정한다(`_slot_parse` 경로).
- 고정한 슬롯의 타일은 `_reserved_except()` 로 다른 슬롯의 후보에서 빠진다.
- **`slot_lock_order` 가 필요하다**: 예약을 다시 잡을 때 슬롯 번호 순으로 돌면 나중에
  고정한 슬롯이 먼저 고정한 슬롯의 타일을 빼앗아 '고정' 약속이 깨진다. 먼저 온 쪽이
  우선이어야 한다.
- `render_belt()` 첫머리에서 `_refresh_locks()` 를 부른다 — 추가·제거·교체·회전·드래그가
  전부 여기로 모이므로 이게 유일한 갱신점이다. 못 잡으면 그 슬롯의 고정을 푼다.
- 고정은 저장하지 않는다("지금 벨트에 대한 계획"). 새 게임/불러오기에서 `clear_slot_locks()`.

### 나침반 유물 재설계 (겹침 해소)
예전: "힌트가 초성 대신 완성 단어를 알려줍니다" → **이제 무료 힌트가 단어를 준다** →
설명이 거짓이 된다. 그래서 유물을 **편의**로 옮겼다:
`relic_initial_compass` = 헤더의 `전체 힌트` 버튼을 열어 **세 슬롯을 한 번에** 채점하고
조합 전체를 한 줄로 보여준다. 슬롯 하나씩 누르면 나머지 슬롯 몫을 알 수 없다.
→ 감독 확인 대기 항목 (다른 설계를 원하면 교체 가능).

### 레이아웃 제약 (실측)
힌트/고정을 **제목 줄에 나란히** 붙였다. 타일 위에 별도 줄을 만들면 트레이가 세로로

2행 y=623~684, 벨트 하단 720 → 2행까지는 잘리지 않는다(여유 36px).
유령 상자는 트레이 폭을 **목표 단어 길이**까지만 넓힌다 — 타일을 다 놓았을 때와 같은
폭이라 새로운 최악의 경우를 만들지 않는다.

## (H) 감사 후속 — '표현되지 않던 로직' 3건

지침(새 콘텐츠 금지 / 로직은 있는데 표현이 없는 것 우선)에 따라 감사 결과를 순위대로 처리.
이번 턴에 처리한 것:

### 1. 타워 누적 피해가 게임오버에서만 보였다
`DefenseField.tower_damage` 는 처음부터 쌓이고 있었고 `damage_ranking()` 도 있었지만,
화면에는 **런 요약(게임오버)** 에서만 나왔다. 즉 "다음 골드를 어느 단어에 넣을까" 라는
이 게임의 핵심 결정을 **감으로** 내려야 했다.

- `DefenseField.total_tower_damage()` / `tower_damage_share(name)` 추가.
  반환: `{damage, total, rank, count}`. **피해 0 도 정보**다 — 한 발도 못 맞춘 타워는
  사거리 밖일 가능성이 크고, 그걸 스펙을 다시 읽으며 추측하게 두면 안 된다.
- `TowerInfoModal.setup(..., p_share)` 9번째 인자. 통계 줄에 두 번째 줄로 붙는다:
  `누적 피해 4,200 (전체의 62%)  ·  1위`. 타워가 하나뿐이면 순위를 붙이지 않는다.
- 런 요약 랭킹에도 비중(%)을 추가 — "1위가 혼자 다 했다" 와 "셋이 나눠 했다" 는
  순위만으로 구분되지 않는데, 그 둘은 완전히 다른 런이다.
- `scripts/ui/NumText.gd` 신설(`NumText.comma`). 같은 값이 정보창은 `4,200`,
  요약은 `4200` 으로 찍혀서 **같은 값이 두 화면에서 다르게 보였다**.
  Palette 에 넣지 않은 이유: Palette 는 스스로 "단일 색상 소스" 라고 못 박고 있다.

### 2. 타입/속성 배지가 같은 색이면 한 축으로 뭉갠다
`질풍`(타입 fast) 색과 `질주`(속성 swift) 색이 **둘 다 주황**(0.95, 0.60, 0.10)이었다.
둘 다 칠하면 똑같은 주황 블록 두 개가 나란히 떠서 '타입 상성' 과 '속성 상성' 이라는
두 축이 화면에서 하나가 된다 — 정작 무엇으로 때려야 하는지가 다시 안 보인다.

→ **색이 아니라 형태로 축을 나눈다.** 타입 = 색으로 꽉 채움(흰 글자),
속성 = 어두운 바탕(`BADGE_ATTR_BG`) + 표의 색으로 1px 테두리 + 그 색을
`lightened(0.3)` 한 글자. `badge_specs()` 가 `[문구, 색, 타입인가]` 3요소를 돌려준다.
실캡처 확인: `질풍`=주황 채움, `질주`=주황 테두리. 색이 겹쳐도 축이 읽힌다.

**일반화**: 같은 색을 쓰는 두 축은 색으로 구분할 수 없다. 형태(채움/테두리)를 쓸 것.

### 3. 테스트도 표를 단일 출처로 삼게 바꿨다
기존 배지 테스트는 r/g/b 임계값(`want_color_g: 0.75`)을 손으로 적어 두고 있었다 —
표를 고치면 조용히 어긋난다. 이제 `MonsterRoster.type_color()` / `attr_color()` 와
직접 비교하고, 타입은 `border_width_top == 0`, 속성은 `> 0` 을 함께 확인한다.

## (H-2) 화상에 지속 표시를 붙였다

화상은 매 프레임 피해를 넣고 있었지만 화면에는 **합산된 피해 숫자**만 떴다. 숫자는 순간이고
화상은 몇 초 이어지는 상태다 — "지금도 타고 있다" 를 보여 주는 것이 없어서, 지속 피해 타워를
사 둔 플레이어는 그 타워가 계속 일하고 있는지 알 수 없었다. (제어 타워가 겪었던 것과 같은
비가시성이고, 그때는 셰이더 색으로 해결했다.)

### 왜 셰이더 색을 안 썼는가
`status_tint.gdshader` 주석이 "화상·중독 같은 상태도 같은 셰이더로 색만 바꿔 쓸 수 있다" 고
적어 두었지만 **실제로는 못 쓴다** — uniform 이 `status_tint`/`status_amount` **한 쌍뿐**이라
상태 하나만 그린다. 감속과 화상은 동시에 걸린다(질주하는 적이 제어 타워와 지속 피해 타워
사거리에 함께 들어가면 실제로 겹친다). 한 쌍을 더 늘리면 주황+파랑이 섞여 둘 다 못 읽게 된다.

→ 화상은 **칩**으로 표현한다. 색 슬롯은 두 축이 나눠 쓸 수 없는 자원이다.
`EnemyUnit._burn_badge`: 어두운 바탕 + `BURN_BADGE_COLOR`(1.0, 0.62, 0.22) 글자,
`화상` / `화상 ×N`(겹수 — 겹수는 색으로는 절대 못 말한다).
`apply_burn` 에서 뜨고, `_tick_burn` 이 다 타면 내린다.
셰이더 파일에 **왜 안 썼는지**를 적어 두었다 — 안 적으면 다음 사람이 unused uniform 을 보고
"고친다".

### 칩은 컨테이너에 담았다
`_slow_badge` 는 스프라이트 아래 `Vector2(-18, 19)` 에 손으로 놓인 Label 이었다. 두 번째 칩을
같은 방식으로 놓으면 **둘이 동시에 뜨는 순간**(= 면역 케이스) 겹친다. 그래서
`_ensure_state_row()` 가 `HBoxContainer`(폭 84, `ALIGNMENT_CENTER`)를 만들고 두 칩을 **함께**
(둘 다 숨김) 넣는다. 순서가 상태 도착 순서에 따라 뒤바뀌지 않는다.
행 자체는 지연 생성이라 화상/면역을 한 번도 안 겪은 적은 노드를 안 만든다(MAX_ENEMIES 50).

`tools/FrameStrip.gd` 가 `e._slow_badge.text`/`.visible` 를 직접 읽으므로 변수 이름과 타입
(Label)을 유지했다 — 리팩터링할 때 진단 도구가 깨지지 않게.

## (I) 슬롯 힌트를 "해석 가능" 하게 — 트레이 머리 재배치 + 행동 한 줄

디렉터가 스크린샷을 붙이며 물었다: **"새로 만들어진 슬롯별 힌트, 고정이 사용하기 좀
어렵네. 이런 식으로 나오면 어떻게 해석해?"** 화면에는 `[ㄱ][ㅣ(금)][ㅇ][ㄴ][ㅏ][ㅏ(금)]`
처럼 보였고, 디렉터는 이걸 **한 단어로 읽었다**. 그래서 없는 단어가 나왔다.

### 실제 원인 3개 (전부 "로직은 있는데 표현이 없다")
1. **목표 단어가 트레이에 없었다.** 채점 색(초록/금색/회색)과 유령 상자는 '무엇을
   기준으로 채점했는지' 를 알아야 읽히는데, 목표는 벨트 헤더 한 줄에만 있었다.
2. **빠진 자모를 칸막이 없이 이어 붙였다.** `[내 타일…][빠진 자모…]` 가 붙어서
   **한 단어처럼** 읽힌다. 실제로 빠진 자모는 목표의 남은 자리를 순서대로 나열한
   것이라 이어 읽으면 반드시 없는 단어가 나온다.
3. **다음에 할 일이 안 적혀 있었다.** 색의 뜻(🟩자리 맞음/🟨옮겨야/⬛안 쓰임)은
   머릿속에 없고, 범례는 타일 툴팁(=호버)에만 있었다.

### 고친 것
- `_add_tile_group`: 트레이 머리에 `TargetLabel`(`목표 <단어>`, 금색) 추가.
  유령 앞에 `NeedLabel`(`필요`) 칸막이 추가(`_build_need_label`, 세로 62px로 타일과 높이 맞춤).
  유령 상자는 `MOUSE_FILTER_PASS` + 툴팁("이 슬롯에 아직 없는 활자입니다 — [단어] 에 필요한 자모").
- `_slot_hint_text`: 행동 문장으로. `부족 ㅇ ㅂ` / `금색 N개는 자리를 옮겨야 함` /
  **`회색 N개는 이 단어에 안 쓰임`**(신규 — 안 쓰인 타일은 '옮기는' 게 아니라 **빼야** 한다.
  이 줄이 없으면 플레이어는 ㄱ 을 맨 앞에 둔 채 ㅇ ㅂ 을 뒤에 붙여 없는 단어를 상상한다) /
  아무것도 없으면 `지금 배치 그대로 완성`.

### 진짜 버그는 따로 있었다 — 트레이 머리 배치
`title.size_flags_horizontal = SIZE_EXPAND_FILL` 이 남는 폭을 **혼자 다 먹어서**,
`[목표 …][힌트][고정]` 이 트레이 오른쪽 끝 63px 안에 뭉쳐 붙었다. 실측:
title rect 181px(글자는 44px) / TargetLabel x=184 / Hint x=237 / Lock x=270 (트레이 302px).
→ `목표 입` 이 버튼 무리에 섞여 **버튼처럼** 읽혔다.

수정: 제목에서 EXPAND_FILL 제거 + 버튼 앞에 `SIZE_EXPAND_FILL` 스페이서.
실측 결과 title 0..44 / target 47..97 / 스페이서 / Hint 237 / Lock 270. 왼쪽은 한 문장,
오른쪽은 액션. 트레이 패널에 `content_margin_left/right = 5` 도 추가(제목 첫 글자가
테두리에 닿았다 — 제목이 가운데서 왼쪽으로 옮겨 오면서 생긴 부작용).

### 회귀 가드 (이게 핵심)

버그를 일부러 주입해 가드가 실제로 실패하는지 확인했다(gap 48.0 → ERROR).

## (K) 힌트가 목표 단어를 그대로 적던 문제 (2026-09-20)

**요청**: "@Clipboard_Screenshot.png 힌트에 직접적으로 목표 단어가 나오면 안되"
(스크린샷 = 트레이 머리 `2번 슬롯 · 목표 수정구`)

### 왜 문제인가
힌트의 존재 이유는 '배치를 돕는 것' 인데(코드 주석이 그렇게 적혀 있다 — 예전 초성
힌트를 버린 이유도 "배치를 돕지 않아서" 였다), 단어를 그대로 적으면 플레이어가 할
일이 **단어를 찾기 → 받아쓰기** 로 바뀐다. 힌트가 아니라 건너뛰기다.

### 새는 통로가 **넷**이었다 (라벨 하나만 고치면 안 됐다)
1. `TargetLabel` — 트레이 머리 `"목표 " + slot_targets[i]`
2. `_slot_hint_text()` — 상태 줄 `"N번 슬롯 목표 [수정구] · 부족 ㅈ ㅓ ㅇ ㄱ ㅜ"`
3. `_show_all_hints()` — `"최적 조합: [수정구] [바나나]"`
4. `_build_ghost()` 툴팁 — `"[수정구] 에 필요한 자모"`
   + `_toggle_slot_lock()` 의 고정/실패 메시지 2곳 (`[%s]`)도 같은 통로였다.

### 고친 방식 — '답' 대신 '모양'
- 머리·상태 줄·전체 힌트: **음절 수**만 (`목표 2음절`, `최적 조합: 1번 2음절 …`).
- 빠진 활자는 **개수**만 (`빠진 활자 3개`).
- **유령 상자는 가나다순으로 흩어 세운다.** 목표 순서대로 세우면 [내 타일…][필요]
  [ㅈ][ㅓ][ㅇ][ㄱ][ㅜ] 가 그대로 이어져 화면에 수정구가 적힌다 — 칸막이(`필요`)가
  있어도 소용없다. 흩으면 '무엇이 더 필요한지' 는 남고 '어디에 놓을지' 는 플레이어 몫이
  된다. 힌트가 도와야 하는 지점이 정확히 그 '배치' 다.
- `Array.sort()` 가 그냥 **가나다순**이 된다: 호환 자모 블록(U+3131~)이 자음→모음
  한국어 순서로 배열돼 있어서 정렬 키를 따로 만들 필요가 없다.

### 남은 위험 (디렉터 판단 필요)
활자 **가나다순 더미**는 짧은 단어에서 여전히 강한 힌트다. 자모 **다중집합**이 곧 답에
가깝기 때문이다(ㅇㅈㅜㅜ → 우주). 다만 3음절 단어(고 tier, 실질적 보상)에서는 더미가
{7자모} 라 실제로 찾을 거리가 남는다 — **보상이 큰 곳에서 덜 새는** 성질이라 그대로 둔다.
더 가리려면 (a) 유령을 `?` 로 개수만, (b) 초성만 노출 중 하나. 아직 미적용.

### 검증
- 가드 2개를 **먼저** 쓰고 옛 코드에서 실패를 확인했다(9건 실패). 통로 넷을 전부 잡았다:
  `목표 우주` / `1번 슬롯 목표 [우주] · 부족 ㅇ ㅜ ㅈ ㅜ` / `[우주] 에 필요한 자모` ×4 /
  유령 순서 `["ㅈ","ㅓ","ㅇ","ㄱ","ㅜ"]`.
- `_hint_texts()` 는 벨트 **전체**를 훑지 않는다. 화면에 '조합 추천' 버튼처럼 게임이 쓰는
  낱말이 이미 널려 있어서, 목표가 하필 그 낱말이면 거짓 실패한다. 통로 넷을 명시한다.
- 전체 6개 스위트 통과(rc=0). 스크린샷: `docs/design/screenshots/hint_no_target_word.png`
  + `_belt.png`(2배 확대 — 10px 글자는 전체 프레임에서 안 읽힌다).


## (L) 힌트·도감의 밸류가 실제 타워 밸류와 **반대**였다 (2026-09-20)

**요청**: "@Clipboard_Screenshot.png 현재 바늘인데, 목표가 가루야. 현재의 타워 밸류가 더
높고, 힌트의 밸류가 더 낮아." (스크린샷 = 벨트에 바늘, 힌트 목표는 가루)

### 원인 — 랭킹이 **죽은 필드**를 읽고 있었다
`AutoArrange._word_score` 는 `tier*1000 + word_data.damage` 였고, **게임플레이 코드는
`word_data["damage"]` 를 한 번도 읽지 않는다.** tier == 음절 수라서 같은 길이끼리의
순서는 전부 이 죽은 필드가 정하고 있었다 — 동전던지기였다.

측정(`tools/HintValueProbe.gd`, 전 DB 366단어): 같은 길이 쌍 **46.5%가 거꾸로**.
리포트된 쌍 실측: 가루 DB damage 44 · 실제 **9.5 DPS** vs 바늘 DB damage 22 · 실제
**45.4 DPS** — 도감이 4.8배 약한 단어를 더 세다고 보여 줬고, 디렉터가 그걸 믿었다.

### 고친 방식 — 값을 **한 곳**에서만 계산한다
- `WordTower.preview_stats(syllable, word_data)` (static) 신설. base·per_hit·**volley**·
  interval·dps·trait·range 를 돌려준다. 힌트·도감·정보창이 전부 이걸 쓴다.
- `AutoArrange.word_value` = `dps * 100` (캐시). `_word_score = word_value + tier` —
  tier 는 **동점 처리용**으로만 남는다.
- `_word_score` 가 1000 스케일에서 100 스케일로 바뀌면서 `PROFILE_BONUS := 700`(7 DPS)
  이 의미를 잃어 세 프로필이 같은 답을 냈다. 매직넘버를 다시 만지지 않고 **프로필이
  후보 풀을 좁히게** 바꿨다(`PROFILE_CATEGORIES`) → 3/3 벨트에서 3개 답이 서로 달라짐.
- **volley 를 빼면 2음절이 2.2배 과소평가된다.** 처음에 빼먹고 22.7 이라고 보고했다가
  45.4 로 정정했다. `attack_target` 은 volley>1 일 때 각 대상에 **full damage** 를 준다.
- 검산: 1/2/3음절 → 12.5 / 34.9 / 73.7 DPS (상수 주석과 정확히 일치).

## (M) 힌트에 네 번째 색 — '돌려야 그 자모가 되는' 타일 (2026-09-20)

**요청**: "@Clipboard_Screenshot.png 힌트안에 회전이 가능하지만 회전 모양이 다른 자모일
경우는 다른 색으로 구분하자"

### 왜 색을 나눠야 하는가
금색('자리만 다름')과 회전('돌려야 그 자모')은 **플레이어가 할 일이 다르다.** 전자는
끌어다 놓으면 되고 후자는 ↻ 를 눌러야 한다. 한 색으로 묶여 있으면 ㅏ 를 ㅗ 자리에
끌어다 놓고 "왜 안 되지" 를 반복한다. 회전 표는 ㄱ↔ㄴ, ㅏ→ㅜ→ㅓ→ㅗ→ㅏ, ㅣ↔ㅡ 다.

### 구현 (`JamoBelt._grade_slot` 이 2단계 → 3단계)
1. 같은 자리(초록) → 2. **이미 그 자모인데 자리만 다름**(금색, `flat[i] == req[j]`)
→ 3. **돌려야 그 자모**(파랑, `can_fill`). 금색을 먼저 집는다: 옮기는 게 돌리는 것보다
싸고, 2단계가 전부 훑고 나면 3단계에 남은 타일에는 '같은 자모' 가 안 남아 있다.
- 색: `GRADE_ROTATE_BG/LINE` = `#173A5E` / `#6FA8FF` (초록·금색·회색과 색상환이 가장 멀다).
  `Palette` 에 파랑 토큰이 없어 `GRADE_*` 옆에 뒀다.
- 툴팁 `_grade_label("rotate")` = "돌려야 이 자모가 됨 (↻)".

### 덤으로 잡은 거짓 등급 — **합자는 회전할 수 없다**
`_grade_slot` 은 합자를 조각으로 펼친 뒤 조각에 `can_fill` 을 걸었다. ㄲ 의 조각 ㄱ 이
회전 가능하다는 이유로 **ㄲ 한 장에 ㄴ 을 채우라고 시키는** 등급이 나왔다(회전 배지조차
없는 타일에). 이제 합자는 '펼친 조각 == 목표 자모' 일 때만 쓰인 것으로 본다 →
`["off","near"]` (옛 코드 `["near","near"]`).

### 덤으로 잡은 잘림 — 힌트 한 줄이 **조용히** 잘리고 있었다
파랑 절을 추가하니 네 번째 절('회색 N개 제외')이 화면 밖으로 밀렸다. `PreviewLabel` 은
`clip_text` 라 넘치면 **말없이** 잘린다. 실측: 옛 문구 **746px** vs 라벨 **592px**
(154px 초과) → 지금 문구 **428px**. 절을 압축했다(`파랑 2개 ↻` / `금색 1개 이동` /
`회색 1개 제외`) — 줄은 **행동**, 툴팁(`_grade_label`)은 **이유**로 역할을 나눴다.

### 검증
- 가드를 **먼저** 쓰고 옛 코드에서 4건 실패를 확인했다(`["near","near"]`, 라벨 '',
  힌트 줄에 '파랑' 없음, 합자 `["near","near"]`).
- 새 가드는 네 색이 **한 슬롯에 다 나오는** 배치(목표 고기 = ㄱㅗㄱㅣ, 타일 ㄱㅏㅁㅡㄱ
  → `["pos","rotate","off","rotate","near"]`)에서 **줄 폭까지** 잰다. 글꼴·문구가 바뀌어
  다시 잘리면 여기서 걸린다.
- 자연 힌트 흐름에서 파랑이 나오는지 확인(일회용 프로브): **8건 중 6건**. 죽은 색이 아니다.
- 전체 6개 스위트 통과(rc=0). 스크린샷: `docs/design/screenshots/grade_rotate.png`
  + `_belt.png`.

### 도구에 추가한 것
`tools/Shot.gd` 에 **`target=0:고기`** — 힌트는 목표를 스스로 고르므로 특정 등급 조합을
재현할 수 없다. 목표를 직접 세우면 같은 화면을 매번 찍을 수 있다. 채점 한 줄도 게임과
같은 `_slot_hint_text` 로 뽑는다(손으로 넣으면 화면이 거짓말을 한다).

### 관찰 (고치지 않음)
2장짜리 슬롯([ㄱ,ㅏ])에 힌트를 누르면 "지금 타일로 만들 수 있는 단어가 없어요" 가 뜬다.
**DB 에 가/나/고 가 없어서 맞는 답이다**(1음절 단어는 굿·갓·기·개 처럼 2~4자모).
다만 타워는 '모르는 단어' 로 세워지므로, 플레이어 입장에서는 타워가 서는데 힌트는
불가라고 말하는 셈이다. 표현을 손볼 여지가 있다.

## (N) 슬롯 힌트가 약한 단어를 목표로 삼던 문제 + 추천 패널의 조작된 숫자

디렉터 보고: "@image#1 이거 가지고 있는 조합으로 만들 수 있는 단어 종류가 많고, 가장
상위가 입구인데 @image#2 슬롯 힌트는 왜 저렇게 나오는거야?"

### 원인 1 — 패널 숫자가 **지어낸 값**이었다 (표현 ≠ 로직)
`TowerDefenseMain._recommendation_line` 이 category 로 특성을 **추측**하고 자체
`base * damage_factor / interval` 표를 곱하는 세 번째 공식을 갖고 있었다. 실측(2음절):

| 단어 | 패널이 인쇄한 값 | 실제 `preview_stats` |
| --- | --- | --- |
| 입구 | 관통 35.6 | **관통 53.1** |
| 보루 | 관통 35.6 | **관통 53.1** |
| 기운 | 연쇄 17.7 | **관통 53.1** (특성 이름까지 틀림) |
| 바늘 | 저격 30.5 | **저격 45.4** |
| 안개 | 지속 23.4 | **지속 피해 34.9** |

→ `WordTower.preview_stats` + `WordTower.TRAIT_NAMES` 로 교체, 자체 표 삭제.
디렉터가 "가장 상위가 입구" 라고 믿은 근거 자체가 깨진 공식이었다(입구·보루가 35.6 동점).

### 원인 2 — 조합 최적화가 단일 슬롯 답을 먹였다
`_show_slot_hint` 가 `best_word_set_for(owned, words, 열린 슬롯 수)` 의 **같은 순번**을
목표로 썼다. 조합은 **총합**을 키우는 계산이라 한 슬롯에 1음절 잔여를 떼어 주는 것이
정상 동작이고, 그래서 타일 7장을 든 슬롯이 '목표 1음절' 을 받았다.
**가드로 잰 값: 목표 기 = 944 vs 만들 수 있는 구름 = 5309 (5.6배).**

→ `_slot_available_indices(slot_index)`(다른 슬롯이 고정한 타일 제외)를 풀로 삼아
`AutoArrange.buildable_words_for(available, all, 1)` — **패널과 같은 순위 함수**.
이제 같은 벨트에서 패널 1위 = 슬롯 힌트 목표 = `구름`. 벨트를 나누는 일은 고정(lock)과
나침반(`_show_all_hints`)이 맡는다.

**이미 같은 계약이 있었다**: `_test_hint_never_prefers_a_weaker_word` (가루 vs 바늘 보고).
같은 형태의 보고가 오면 새 계약을 만들기 전에 기존 가드를 먼저 grep 할 것.

### `_regrade_slots` 는 **고치지 않았다**
벨트 전체로 판정하는 것이 맞다. 목표는 '지금 이 슬롯 타일의 채점표' 가 아니라 **도달할
단어**이고, 타일을 끌어다 넣는 것이 정상 흐름이라 아직 안 넣은 활자(유령 상자)가 있어도
목표는 살아 있어야 한다. 슬롯 기준으로 바꿨더니 유령 상자 기능이 통째로 죽었다
(유령 = 목표에 필요한데 슬롯에 없는 활자 → 슬롯 기준이면 missing 이 항상 비어 있다).
기존 테스트 2건이 정확히 이 계약을 잠그고 있었다.

### 스크린샷 두 장은 **같은 상태가 아니었다**
패널 스크린샷이 `바기` 를 보여 줬는데, 그 단어는 두 DB 파일 어디에도 없다(265 + 100,
전부 NFC). 즉 그 패널은 현재 DB 이전 상태다. 반면 벨트 스크린샷은 프로브로 재구성해
확인: `best_word_set_for(...,3)` = `[구름, 곡, 기]` → 1번 슬롯 2음절 · 3번 슬롯 1음절,
**스크린샷 라벨과 정확히 일치**. 이미지에서 추론하지 말고 프로브로 재구성하는 것이 이겼다.

### 검증
- 가드를 **먼저** 쓰고 옛 함수로 되돌려 실패 확인:
  `got '기', best '구름'` / `target 기 = 944, best = 5309` — 이 출력이 진단서다.
- 전체 6개 스위트 통과(rc=0).
- 스크린샷: `docs/design/screenshots/slot_hint_best_word.png`(+`_belt`),
  `recommendation_panel_real_values.png`(+`_crop`).
- `tools/Shot.gd` 에 **`recommend=1`** 추가(같은 벨트에서 힌트와 패널을 나란히 캡처).

### 남은 긴장 (디렉터 결정 필요)
슬롯 힌트가 이제 슬롯마다 독립적으로 '가장 센 단어' 를 고르므로, 여러 슬롯이 **같은
단어**를 목표로 세울 수 있다(타일을 나눠 쓰지 않는다는 뜻). 벨트를 나누는 화면은
나침반과 고정이다. 슬롯 힌트에도 분배를 반영할지는 디자인 결정.
