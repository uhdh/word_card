## `agent lite` 는 무슨 모델인가 — **자기 자신이었다**

디렉터 질문: "agent lite는 어떤 모델을 쓰는거야?"

### 확인 경로
1. `~/.workbuddy-ai/cache/acc-product-config-v3.json` (클라이언트가 캐시한 서버 제품 설정, 370KB)
   → `/models[]` 의 각 항목에 `relatedModels.lite` 가 있다. **전역 별칭이 아니라 모델별 티어**다.
2. 오늘 SDK 대화 로그: `method:sendPrompt {"modelId":"deepseek-v4.1-flash"}` — 세션 모델 확인.
   로그에는 `lite` 흔적이 **0건** → 해석은 서버에서 일어난다(클라이언트가 안 남김).

### 결론
**`deepseek-v4.1-flash` 의 `relatedModels.lite` = `deepseek-v4.1-flash` — 같은 모델.**
즉 이 세션에서 `model: "lite"` 로 위임하면 **비용 절감이 0** 이다. 저렴한 모델이 아니다.

다른 모델로 가는 것은 딱 둘:
| 세션 모델 | lite 해석 | 절감 |
|---|---|---|
| `default-model` (Auto) | `default-model-lite` | 있음(내부 별칭, 백엔드 미공개) |
| `kimi-k3` | `kimi-k3-1` | 있음 |
| 그 외 선택 가능 모델 전부 | 자기 자신 | **없음** |
| `fast-model`·`balanced-model`·`primary-model`·`deep-model`·`gpt-6-astra`·`hy4-preview*` | 매핑 없음 | n/a |

### 대안 — 명시적 모델 id (검증함)
`model` 파라미터는 `default`/`lite`/`reasoning` 외에 **구체적 id 도 받는다**.
`model: "glm-5.3-flash"` 로 프로브를 돌려 정상 수락·실행됨을 확인했다.
당시 credits: `deepseek-v4.1-flash-sg` x0.03 · `glm-5.3-flash` x0.06 (저렴한 축),
`gpt-5.5`/`primary-model` x3.31 (비싼 축).

**중요**: `deepseek-v4.1-flash` 자체가 `credits: x0.00` 이고 2026-08-06~09-25 무료 프로모션 중이다.
→ **지금은 절감할 비용이 애초에 없다.** 위임의 근거를 "돈"이 아니라 컨텍스트 위생/속도로 말해야 한다.

### 스킬 수정 (거짓 서술 제거)
`planner-implementer` 스킬이 `model: "lite"` 를 "cheap-executor routing value" 라고 단정하고 있었다
— 이 환경에서 **거짓**이다. §4.1 을 신설해 ①모델별 해석 ②확인 명령 ③측정표 ④명시적 id 대안
⑤credits 확인 ⑥근거의 한계(캐시된 설정 + 서버측 해석)를 적었다. §10 의 사용자 보고 문구도
"저렴한 모델에 위임했습니다" → **실제 실행된 모델명을 밝히고 절감을 주장하지 않기**로 고쳤다.
안티패턴에 "`lite` = 더 싸다 가정" 추가. (405줄, YAML·펜스·헤딩 재검증 통과)

## (Y) 몬스터 표시 크기 확대 — "그림은 그대로, 보이는 크기만"

디렉터 지시: "몬스터들이 너무 작은데, 그림은 그대로 사용하되, 게임내에서 좀 크게 나타내줘.
특히 보스는 다른 몬스터보다 크게"

### 실측으로 확인한 출발점
- 타워 지름 ≈ 64~76px, 잡몹 **가시 크기 ≈ 31px** → 정확히 절반. 이게 "너무 작다" 의 정체.
- 아트는 32x32 이고 `Sprite` 는 36x36 `TextureRect`(`stretch_mode=5` KEEP_ASPECT_CENTERED)
  → 이미 1.125배 확대 중. `default_texture_filter=0`(Nearest) 라 확대해도 픽셀 안 뭉개진다.
- 길(`RoadGlow`) 폭 = 54px. 잡몹은 이 안에 들어와야 하고 보스는 넘어가도 된다.

### 결정
- 잡몹 상자 36 → **52px** (+44%). 가시 ≈45px (길 54px 안).
- 보스 배율 **1.9 유지** (기존 값 그대로) → 52 x 1.9 = 99px, 가시 ≈85px.
  배율을 줄이지 않은 이유: 디렉터가 "특히 보스는 크게" 라고 했으므로 기존 강조를 약화시키지 않는다.

### 진짜 문제는 크기가 아니라 **장식 좌표가 두 곳에 박혀 있던 것**
체력바(y -26..-20), 배지 줄(-44), 상태 칩(+19) 이 전부 **36px 상자를 전제로** 씬과
스크립트에 각각 하드코딩돼 있었다. 상자만 키우면 체력바가 몸통에 파묻히고 칩이 발에 붙는다.
→ `EnemyUnit._apply_visual_layout()` **한 곳**에서 상자 크기에서 파생시키도록 고쳤다.
`_setup_badges()` / `_ensure_state_row()` 도 줄을 만든 직후 이 함수를 부른다(계산 지점 단일화).
`_state_wrapper` 멤버 추가 — 칩 줄은 `PRESET_FULL_RECT` 라 **껍데기**가 위치를 들고 있었다.

### 두 번째 함정: **그림이 캔버스를 다 채우지 않는다**
캔버스 끝을 기준으로 장식을 붙였더니 보스 체력바가 **머리 위 25px** 에 떴다(스크린샷으로 발견).
아트의 알파 bbox 를 재보니 32px 기준 위쪽이 4~7px 비어 있었다(고블린 4, 정령 5, 슬라임·보스 6~7).
보스는 배율 1.9 라 그 틈도 1.9배로 벌어진다.
→ `Texture2D.get_image().get_used_rect()` 로 **비율**을 재서 그 위끝/아래끝에 장식을 붙인다.
  경로별 캐시(`static var _ART_BOUNDS`). 실패하면 캔버스 전체로 폴백(예전 동작).
  압축은 꺼져 있다(`vram_texture: false`, `compress/mode=0`) → `get_used_rect` 안전.

### 세 번째 함정: **걸음 프레임이 idle 보다 아래로 더 뻗는다**
idle 만 재면 **정지 화면에서는 멀쩡하고 걸을 때만** 상태 칩이 발을 밟는다(실측 겹침 2.5px).
보스 +3px, 슬라임 +2, 용 +2, 고블린 +1. → idle + 걸음 4장의 **합집합**으로 잰다.
게다가 idle 아트는 **임포트된 512x512** 인데 걸음 프레임은 **임포트 안 된 32x32 파일**이다
(`.import` 가 없다). `load()` 로는 null 이 온다 — `_load_tex`(파일 직접 읽기)를 지나야 한다.
비율로 재므로 크기 차이는 문제없다.

## (Z) 타워를 감싼 원 제거 + 타워 그림 확대 — 2026-09-22 (디렉터 지시)

지시: **"타워가 동그란 원으로 둘러 쌓여 있는데 이거를 삭제해줘. 타워의 크기도 더 키워줘."**

### 먼저 '어느 원인지' 를 확정했다 (추측 금지)
화면에는 원이 **두 종류** 있었다.
1. **빈 발판** `SlotBg` — 지름 64px, 라벤더 테두리 + 반투명 보라 채움 + `"+"`.
   실측: 8개(타워 3개가 쓰는 자리는 숨겨진다). 이건 '여기 세울 수 있다' 는 **기능 표시**라 지우면 안 된다.
2. **타워 자신을 감싼 원** — 지름 **78px**.

판정 근거: 지시문이 "**타워가** … 둘러 쌓여" 라고 했다. 빈 발판은 타워가 아니라 빈 땅이고 `"+"` 가 있다.
그리고 "타워의 크기**도**" 가 한 문장으로 이어지므로 둘 다 **타워 외형**에 대한 불만이다.

### 그 원의 정체 — 그림자가 아니라 '투명 카드의 그림자'
`WordTower._apply_visual_style()` 이 카드에 `shadow_color(0,0,0,0.45)` + `shadow_size 2` 를 주는데,
같은 스타일의 `bg_color` 가 **완전 투명**이다. 그림자는 배경에 가려지지 않으므로 **카드 모양 그대로**,
즉 `corner_radius = 38` 인 **꽉 찬 검은 원판**이 된다. 씬(`WordTower.tscn` 의 `StyleBoxFlat_card`)에도
같은 값이 박혀 있어서 **양쪽 다** 고쳐야 했다(한쪽만 고치면 다른 쪽이 원을 되살린다).

측정(빈 발판 화면 대비 밝기비, 타워 자리 중심):
```
 r-band   타워/빈발판      해석
 18..30     0.64~0.66     원 안쪽이 35% 어둡다
 33..39     0.55~0.76     ★ 발판(r=32) 바깥인데도 어둡다 → 원이 39까지 뻗는다
 39..43     1.000         같아짐
 43..      1.000         완전히 같음
```
즉 타워는 '작은 그림 + 지름 78px 검은 원' 이었다. 수정 후 r=39 부터 **픽셀이 완전히 동일**.

### 죽은 코드 하나를 같이 지웠다 (보고 대상)
`WordTower._draw_socket()` 은 **아무도 부르지 않는다**(전 저장소 grep 결과 호출부 0).
그런데 `_apply_visual_style()` 주석은 "타워 구분은 (1) `_draw()` 의 라디얼 소켓, (2) 카테고리 색 호,
(3) 그림자" 라고 **단정**하고 있었다 — (1)(2)는 실제로 그려지지 않으므로 거짓이다.
지시가 '원 삭제' 이므로 소켓(원을 그리는 함수)과 `SOCKET_*` 상수를 지우고 주석을 사실에 맞췄다.
**부작용: 타워에는 지금 '카테고리 색' 단서가 화면에 전혀 없다**(툴팁에만 있다). 소켓이 그걸 하려던 장치였다.
→ 되살릴지 여부는 디렉터 결정.

### 크기 상한은 '발자국 40px' 이고, 아이콘마다 다르다
- 발판은 길 옆에 붙어 있다. `PAD_RADIUS(32) + PAD_ROAD_GAP(8) = 40` 이 상한(코드 주석이 계약).

- 아이콘은 32x32 캔버스를 꽉 채우지 않는다. 상자 크기가 아니라 **칠해진 픽셀의 최대 반지름**으로 재야 한다.

라벨은 **22자 상한**(정보창이 그보다 긴 라벨을 조용히 버림) — 최장 20자, 테스트가 잠근다.

## (AG) 특성 설명 ↔ 코드 계약 감사 — 다중 타격 5종에서 위반 2건 발견

**계기**: G1 은 디렉터 결정이 필요해 멈춰 있고, 그 사이 "설명이 계약" 원칙에 더 정확히
맞는 후보를 찾으라는 흐름. 이월 항목이었던 `splash` 설명("주변의 **모든** 적")과
`_trait_targets()` 의 상한 3 이 어긋난다는 것을 **측정으로 확정**했다.

### 측정 (신규 상설 도구 `godot/tools/TraitBlastProbe.gd` + `.tscn`)

사거리 안 적 7마리 · **주 타깃 18~34px 안에 3마리 밀집** · `get_enemies()` 순서는 '먼쪽 먼저'.
`attack_target()` 이 실제로 부르는 `_trait_targets()` 와 `damage_shares()` 를 직접 부른다
(표를 베껴 두지 않는다).

| 특성 | 설명이 약속한 위치 | 뽑힌 적 (주 타깃 기준) | 선택 | 총 피해 ÷ 발당 |
|---|---|---|---|---|
| splash | 착탄 지점 주변 | 0 · **149** · **176** px | 3 | 11.34 ÷ 11.34 = ×1 |
| pierce | 뒤편 | 0 · 118 · 139 px | 3 | 18.41 ÷ 18.41 = ×1 |
| chain | 적중한 적 주변 | 0 · 204 · 241 px | 3 | 7.14 ÷ 7.14 = ×1 |
| bounce | 주변 적들 사이 | 0 · 165 · 195 px | 3 | 25.20 ÷ 8.40 = **×3** |
| control | 착탄 지점 주변 | 0 · 319 · 377 px | 3 | 4.62 ÷ 4.62 = ×1 |

→ **밀집 3마리는 다섯 특성 모두 0마리 뽑혔다.** 대상을 정하는 것은 위치가 아니라
**스폰 순서**다 — `_volley_targets()` 는 진행도 순 정렬이 있는데(`:643`)
`_trait_targets()` 에는 없다. 이게 "왜 저 적을 때렸지" 를 설명 불가능하게 만든다.

### 위반 2건

1. **splash 는 설명·연출·테스트가 "착탄점 폭발" 을 계약으로 걸어 두었는데 로직만 다르다.**
   - 설명 `TraitStyle.gd:33` "착탄 지점 주변의 **모든** 적"
   - 연출 `Juice.gd:152` 착탄점 38px 폭발 고리 — 그 주석이 근거로 든 문장이 바로 그 설명이다
     (`Juice.gd:128` "설명이 계약이다")
   - 테스트 `test_tower_traits.gd:541` 이 splash = 25점 닫힌 고리를 **고정**한다
   - 그런데 피해는 착탄점과 무관 + 총량이 나뉜다 → "모든 적" 도 "폭발 피해" 도 아니다
   → 셋 중 둘이 서로 맞고 **로직만 혼자 어긋난다.**

2. **`동시 타격 N마리` 툴팁이 2음절 이상에서 거짓말이다.**
   `bonus_targets` 는 `_trait_targets()` 에서만 읽히는데 2음절 이상은 `_volley_targets()` 로
   빠진다 → 유물 "대상 +1" 이 **아무 데도 안 쓰인다**. 툴팁은 여전히 `3 + bonus_targets` 를 말한다.
   - 산(1음절) 툴팁 4 · 실제 **4** ✅ / 산가(2음절) 4 · **2** ❌ / 산가나(3음절) 4 · **3** ❌

### 고치지 않고 기록만 한 이유
원칙이 우선하라고 한 것은 "로직은 있는데 표현이 부족한 것" 인데 여기는 **반대**다
(표현이 로직보다 앞서 있다). 어느 쪽을 맞출지(설명을 낮출지 / 로직을 올릴지)는 밸런스
판단이고, 난이도 게이트가 이미 "너무 쉽다"(120% > 75%)로 실패 중이라 임의로 정할 수 없다.
→ `docs/design/04_TD_BENCHMARK_AND_DEPTH_GAPS.md` **§2.7** 로 실측 기록 + §6 에 결정 대기로 명시.

### 도구 교훈 (새로 추가 — 중요)
- **`Edit` 의 `old_string` 이 들여쓰기 블록 안에서 시작하면, 툴이 공백을 정규화해 매칭한 뒤
  `new_string` 을 그대로 써 넣어 블록이 바깥 스코프로 빠져나갈 수 있다.** `SaveManager.gd`
  의 `_is_test_run()` 에서 실제로 발생 — `for` 루프 **밖**으로 나가서
  `Identifier "a" not declared` 파싱 에러. **성공 메시지는 정상으로 나왔다.**
  → 들여쓰기 블록을 건드린 뒤에는 **반드시 그 구간을 다시 읽고** 인수 명령(테스트)을 돌릴 것.
- 상설 도구를 새로 만들면 `SaveManager._is_test_run()` 에 **이름을 추가**해야 한다
  (실제 세이브를 덮지 않기 위해). 이번에도 추가했다.
