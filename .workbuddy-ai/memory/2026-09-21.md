`[살 타워] > [지옥불 타워] > [도깨비 타워]` — 그런데 필드에 도깨비 타워가 없다)

## (O) 결론 — 파서가 도깨비를 만들 수 없었다. **사전 전체에서 유일하게.**

### 원인: 같은 자모 열을 두 해독기가 다르게 읽는다
자모 열을 읽는 곳이 **두 군데**이고, 서로 다른 함수다.

| 화면 | 해독기 | 도깨비의 열 `ㄷㅗㄱㄱㅏㅣㅂㅣ` 를 |
|---|---|---|
| 슬롯 힌트 · 채점(`_grade_slot`) | `AutoArrange.required_jamo` | **도깨비** (정확) |
| 타워 생성(`parsed_slots` → 파서) | `HangulStreamParser.parse_jamo_stream` | **독개비** (미지의 활자) |

그래서 슬롯은 8장 전부 `pos`(초록, "제자리") · 헤더 "목표 3음절" 인데, 필드에는
도깨비가 아니라 **`독개비` 미지의 활자 타워**가 섰다. 화면은 "맞다" 고 말하고
필드는 다른 것을 세우니 플레이어가 할 수 있는 일이 없다 — **로직은 있는데 표현이 거짓말**.

### 파서 쪽 정확한 실패 지점: `_prefer_registered_jong_split`
도깨비 = 도 + 깨 + 비. 깨 = **ㄲ + ㅐ**, ㅐ = **ㅏ + ㅣ** → 열이 8장인 이유.
종성을 붙일지 저울질하는 그 함수가 **다음 음절의 중성 합성을 빼먹었다**:

```
split_prefix  = "독"                     (ㄱ 을 도의 받침으로)
double_prefix = "도" + compose(ㄲ, jamo_list[index+2])   ← index+2 = ㅏ 한 장만 봄
              = "도까"                   ← 실제로는 "도깨"
```
`'도까' 로 시작하는 단어는 없다` → 등록된 `'독'` 쪽 선택 → 열이 독개비로 굳는다.
자음 경계(ㄱ+ㄱ→ㄲ)는 기존 테스트 `_test_parser_prefers_registered_word_at_double_consonant_boundary`
(`궁극기`)가 잠그고 있었지만 **모음 경계(ㅏ+ㅣ→ㅐ)는 비어 있었다.**

### 사전 전체 감사 결과 — 정확히 1개
사전 365개 중 2음절 이상 284개를 `required_jamo(word)` → 파서 왕복:
- 수정 전: **1개 실패 — `도깨비(ㄷㅗㄱㄱㅏㅣㅂㅣ)→독개비`**
- 수정 후: **0개 실패**

즉 **도깨비는 이 게임에서 자기 자모 열로 만들 수 없는 유일한 타워였다.**

### 수정
1. `_compose_jung_at(jamo_list, index) -> {"vowel","used"}` 신설 — 삼중(ㅗ+ㅏ+ㅣ→ㅙ) →
   이중(ㅏ+ㅣ→ㅐ) → 단일 순서. **중성 규칙을 한 곳에만 둔다.**
2. `parse_jamo_stream` 의 중성 결정 블록이 그 함수를 쓰도록 정리(동작 보존 리팩터).
3. `_prefer_registered_jong_split` 이 `next_jung := _compose_jung_at(jamo_list, index+2)`
   로 다음 음절 중성을 **합성해서** 본다.

### 이번에 배운 것 (다음 보고에 쓸 것)
- **`pos`(초록)는 '정확히 같음' 이다.** `_grade_slot` 1단계가 `flat[i] == req[i]` 이고,
  회전해서 맞는 타일은 별도 등급 `rotate`(파랑)다. 그래서 **"전부 초록" 은 타일 열이
  `required_jamo` 와 완전히 같다는 증거**다 → 픽셀로 ㅜ/ㅗ 를 다시 읽을 필요가 없다.
  (이번에 픽셀 판독으로 ㅜ·ㄴ 이라고 잘못 읽었고, 초록이라는 사실이 그걸 즉시 반박했다.
  픽셀 글리프 감식은 이 게임에서 이미 두 번 실패했다 — 등급·개수 같은 **구조적 단서**가 이긴다.)
- `바기` 는 DB 에 없어도 정상이다 — `make_unknown_word_data` 가 만드는 **미지의 활자**가
  미리보기에 `[바기 타워]` 로 뜬다. "DB 에 없으니 다른 빌드" 라는 추론은 틀렸다.
- 미리보기 라벨과 타워 생성은 **같은 `parsed_slots()`** 를 읽는다 → 이 둘은 갈릴 수 없다.
  갈리는 것은 `required_jamo`(힌트·채점·추천) ↔ 파서(타워 생성) 축이다.
- 사전 왕복 감사는 프로브로 5분이면 돈다. **"그 열로 만들 수 있나" 를 물을 때
  스크린샷을 읽지 말고 `required_jamo` → 파서 왕복을 돌려라.**

## (P) 결과 화면이 필드 효과에 덮이던 문제 + 순위표가 칸을 안 맞추던 문제

감독 보고: **"끝나고 결과 화면이 꽉차서 안보이고, 회전 아이콘이 위로 보인다"**

### 원인 1 — `ModalLayer` 가 CanvasLayer 가 아니라 그냥 Control 이다
그래서 **z_index 가 트리 전체에서 하나의 순서로 비교된다.** 게임 트리 노드의 z 가 모달의
z 이상이면 모달 **위에** 그려진다. 그런데 이 프로젝트의 z 사다리는 이랬다:

| 노드 | z |
|---|---|
| DefenseField / JamoBelt 배너 | 120 |
| DefenseField 골드 라벨, EnemyUnit 라벨 | 100 |
| DefenseField 골드 조각 6개 | 99 |
| Juice fx | 98 |
| 모달(상점·도감 등, z 를 명시한 것들) | 50 / 60 / 80 |
| **`_on_game_over` 런 요약 모달** | **0 — 아예 안 잡았다** |

즉 런 요약은 필드의 **골드 라벨과 골드 조각 6개에 덮여** 있었다. 프로브가 이름까지 찍었다:
`VBox/FieldContainer/DefenseField/@Label@197 z=100 pos=(588,322)`,
`.../@ColorRect@198 z=99 pos=(572,310)` (6개), 모달은 `z=0`.

**호출부를 고치면 다음 모달에서 또 난다** — 상점·도감·타워 정보창도 같은 이유로 필드 효과
아래에 깔린다. 그래서 `scenes/TowerDefenseMain.tscn` 의 ModalLayer 에 **`z_index = 200`**
(게임 트리 최대 120 보다 위) 한 줄을 주고, 천장 자체를 계약으로 잡았다.
`z_as_relative` 가 기본 true 라 모든 모달 실효 z = 200 + 자기 z 가 되고, 게임 트리(≤120)는
전부 아래로 내려간다. 이유는 `modal_layer` @onready 주석에 적어 두었다.

### 원인 2 — 순위표를 줄마다 가운데 정렬한 Label 로 찍고 있었다
`"%d위   %s 타워   %s  (%d%%)"` 를 한 줄 Label 에 담아 **줄마다 가운데 정렬**. 비례폭 폰트라
공백 패딩은 아무 효과가 없어 '1위' 와 '3위' 의 시작점이 다르고 피해 숫자가 세로로 하나도
맞지 않았다 → 표가 아니라 문장 덩어리. **런 요약은 결산 화면이라 여기서 "누가 일했나" 가
한눈에 안 들어오면 요약의 뜻이 없다.**
→ 4열 `GridContainer`(순위 | 이름 | 피해(우측) | 비중(우측)), 표는 패널 폭을 쓰고,
결산 항목은 2열 격자로 표의 **왼쪽 끝**에 맞춘다. 칸 폭은 격자가 정한다 — 셀은 폭을
주장하지 않고 정렬·색만 정한다.

### 가드
`_test_the_modal_layer_stays_above_everything_else` (tests/test_tower_traits.gd)
- `_effective_z()` 로 **실효 z** 를 계산한다(z_as_relative 면 조상 z 를 모두 더한다).
- 실패 메시지 2단: ① `ModalLayer must own a layer above the game tree, but its effective z is 0`
  ② `Nothing in the game tree may draw at or above ModalLayer (z=0), but: TopBar(z=10), …`
- 함정 2개: (a) **ModalLayer 자기 자신을 제외**해야 한다(`is_ancestor_of` 는 자기에게 false).
  (b) `z != 0` 인 노드만 보고해야 한다 — 천장이 0 일 때 `z >= ceiling` 은 기본 레이어 노드
  ~150개를 나열해 신호를 묻는다.
- 옛 코드로 되돌려 실패 확인함(rc=2).

### 이번에도 픽셀 판독이 졌다
모달 위의 작은 원+화살표를 **회전 배지**로 의심하고 오래 붙들었다. 결정적 실험은
**벨트를 비운 채 같은 요약을 캡처**하는 것 — 그래도 그 모양이 있으면 타일 배지일 수 없다.
그러면 프로브가 `z` + **부모 경로** + `pos` 를 찍어 정체를 확정한다. `@Label@197` 만으로는
아무것도 모르지만 `.../DefenseField/@Label@197` 이면 소스의 어느 `z_index = 100` 인지 안다.
픽셀 감식이 진 것이 이 프로젝트에서 네 번째다.

## (Q) 역대 런 랭킹 시스템 + `game_over` 중복 발화

디렉터: **"랭킹시스템을 만들고 싶어."** (키·저장 위치·노출 위치는 확정되지 않아 가정하고 진행)

### 가정한 것 (디렉터가 다르면 알려 주면 됨)
1. **순위 키 = 점수를 지어내지 않고 관찰 가능한 사실만.** `SaveManager.run_ranking_is_better`
   한 곳: **이겼는가 → 막 → 라운드 → 총 피해**. 가중치를 만들지 않았다 — 이 프로젝트는
   이미 자체 공식으로 DPS 를 지어내 어긋난 적이 있고(추천 패널), 랭킹은 "누가 더 나았나" 를
   정하는 자리라 여기서 숫자를 지어내면 순위 전체가 거짓말이 된다.
2. **저장 = 영구 파일 분리.** `user://run_ranking.json` (+`_test` 변종). 진행 세이브에 얹으면
   '새 게임' 한 번에 역대 기록이 날아간다(도감과 같은 이유). 상위 10개만 유지.
   `_is_test_run()` 을 재사용하려고 `SaveManager` 안에 넣었다 — 플레이어 세이브 보호 규칙이
   한 곳에 있어야 한다.
3. **노출 = 런 요약 화면.** 방금 끝낸 사람이 가장 알고 싶은 것이고, 다른 화면에 숨기면
   아무도 안 본다. `역대 기록 · N회 중 M위` + 상위 10줄 표, **이번 런은 금색 강조**
   (`submit_run` 이 `index` 를 돌려준다 — 값 비교로 화면에서 다시 찾으면 동점 런에서
   엉뚱한 줄이 강조된다).

### 같이 고친 것 — `game_over` 는 한 번만 오지 않는다
`DefenseField._on_enemy_reached_base` 는 `base_hp = maxi(0, base_hp - dmg)` 뒤
`if base_hp <= 0: game_over.emit(false)` 를 한다. **HP 가 이미 0 이면 기지에 닿는 적마다
신호가 또 온다.** `_on_game_over` 는 호출될 때마다 결과 모달을 새로 만들고 있었다 →
모달이 겹겹이 쌓인다(**'결과 화면이 꽉 차서 안 보인다' 에 이 형태가 섞여 있었다**).
가드를 넣어 확인: 3회 호출 → 모달 3개, 기록 3건. `_run_recorded` 플래그로 1회만 처리하고
`start_new_game()` 에서 푼다.

### 가드 (모두 실패를 먼저 확인했다)
- `_test_run_ranking_orders_by_progress_then_damage` — 승리 > 진행 > 피해, 비대칭성, 자기비교 금지
- `_test_run_ranking_keeps_only_the_best_ten` — 12건 넣어 10건만 남고 최약 2건 탈락
- `_test_run_ranking_reports_the_new_runs_rank` — rank/index/total
- `_test_game_over_records_the_run_only_once` — 3회 호출 → 기록 1건, 모달 **증가분** 1개
  (절대 개수로 세면 씬이 스스로 연 모달 때문에 환경에 따라 달라진다 — 실제로 이 때문에
  스위트에서만 실패했다. 세이브가 남아 있으면 메인 씬이 불러오며 모달을 하나 연다)

## (R) 안전밸브(적 50마리)가 보이지도 않고 이유도 말하지 않던 문제

백로그에서 **"로직은 있는데 표현이 없는"** 항목을 골라 처리했다(감독 지시 우선순위).

### 확인한 사실
- `DefenseField.MAX_ENEMIES = 50`. `_process` 에서 **동시 생존 적이 50 에 닿으면 그 자리에서

- 기지 HP 도 50, 누출 피해도 1 → '50' 이 두 곳에서 서로 다른 의미로 등장하는데 하나도 설명이 없었다.

### 고친 것 (규칙 변경 없음 — 표현만)
1. 위험 구간에서만 분모를 낸다: `적 40 / 50 ⚠` + `Palette.HP_DANGER`. 평소엔 `적 12`.

## (S) 훈민정음의 나침반 — "힌트를 사서 눌렀는데 결론이 화면에 없다" (완료)

### 찾은 것 (디렉터 지침: 로직은 있으나 표현이 부족한 사건)
`relic_initial_compass`(35G)는 벨트 전체를 빔 서치해 세 슬롯의 최적 조합을 찾는다.
그런데 헤더 한 줄은 이렇게만 말했다:

```
최적 조합: 1번 1음절   2번 1음절   3번 1음절
```

**이 줄은 내용이 없고, 게다가 모호하다.** 실측(감·날·굴을 세워 둔 벨트):

| | |
|---|---|
| 지금 서 있는 것 | 감 + 날 + 굴 = **41.0 DPS** |
| 나침반이 찾은 것 | 문 + 골 + 날 = **54.3 DPS** (32% 증가) |
| 화면이 말한 것 | `1번 1음절  2번 1음절  3번 1음절` |

플레이어는 이미 1음절 타워 3개를 세워 뒀으므로 **"바뀌는 게 없다"** 고 읽었다.
35G 를 주고 산 힌트가 찾아낸 32% 를 화면이 표현하지 못한 것이다.
게다가 `N번 M음절` 은 트레이 머리가 슬롯마다 `목표 N음절` 로 이미 말하고 있어 **중복**이었다.

### 왜 그런 줄이 나왔나
`word_value` 는 **실제 타워 DPS×100** 이다(DB `damage` 가 아니다). 그래서 조합의 총 세기를
비교할 수 있는데도, 줄은 그 값을 쓰지 않고 '모양' 만 나열했다. 비교는 공짜였는데 안 했다.

### 고친 것 — `_all_hint_text()` (JamoBelt.gd)
세 경우를 구분하고, 셋 다 '최적 조합의 총 세기' 를 말한다(그건 나침반만 아는 값):
```
최적 조합: 지금 배치 그대로 완성 (54.3 DPS)
최적 조합: 지금 41.0 → 54.3 DPS  (회전 6 · 이동 1)
최적 조합: 최고 54.3 DPS  (회전 6 · 이동 1)     # 슬롯이 아직 단어를 못 이룰 때
```
- 세 번째 분기가 필요한 이유: **단어를 못 이룬 슬롯에는 '지금' 이 없다.** 0 으로 세면
  없는 상승분을 지어낸다.
- '그대로 완성' 판정은 **총점이 아니라 단어 구성**을 견준다 — 값이 같아도 구성이 다르면
  '그대로' 가 아니다.
- `_work_suffix()` 가 색을 한 덩어리로 접는다: 색만으로는 '한 장 밀기' 와 '여섯 장 부수기'
  가 똑같이 파란 타일 몇 개로 보인다.
- 단어는 여전히 쓰지 않는다.

### 가드 (`test_tower_traits.gd`, 기존 테스트 확장)
- 옛 가드는 **형식 잠금**(`"   "` 로 자른 조각이 `음절`/`채점 불가` 로 끝나야) 이었다.
  계약 자체로 바꿨다: `DPS` 를 말하는가 / 완성과 상승을 구분하는가 / **목표 단어를 쓰지
  않는가**. 형식이 바뀌어도 살아남고 더 강하다.
- 단어 누출 검사는 **고정 낱말을 먼저 걷어낸 뒤** `contains()` 한다 — 안 그러면 1음절 목표
  `조` 가 `조합` 안에서 걸려 거짓 양성이 난다.
- **주입으로 물리는지 확인**: 옛 본문을 넣으니 4개 실패. 결정적 증거는
  `(got '…1번 1음절…', done '…1번 1음절…')` — 달라야 하는 두 문자열이 **완전히 같았다.**

### 일부러 안 고친 것 2가지 (과한 수정 제외)
1. **판정 줄은 다음 상호작용에 지워진다.** `render_belt()` 가 `자동 완성 타워: …` 로 덮는다.
   판정은 결정하는 순간 한 번 읽히면 역할이 끝나므로 허용. **계획은 남는다** — 색·유령 상자·
   `목표 N음절` 은 매 렌더마다 `slot_targets`/`slot_grades` 에서 다시 계산된다.
   (새 라벨을 만들거나 `render_belt` 가 보존하게 하는 건 과하다)
2. **슬롯 버튼은 설명과 취소를 겸할 수 없다.** 나침반 뒤에는 모든 슬롯 버튼이 `취소` 라,
   문장을 읽으려 누르면 계획이 지워진다(실측 `target '문' -> ''`). 색 + 타일 툴팁
   (`채점: 돌려야 이 자모가 됨 (↻)`) + `목표 N음절` 이 같은 내용을 덮으므로 그대로 두고 보고.

### 거짓 경보를 하나 밟았다 (중요)
헤더 라벨은 `clip_text = true` 라 넘치면 조용히 잘린다. 그래서 폭을 재 봤더니 내가 손으로 쓴
`3번 목표 3음절 · 빠진 활자 2개 · 파랑 3개 ↻ · 금색 1개 이동 · 회색 2개 제외` = **545 px 로
"잘림"** 이 떴다. 같은 기능의 두 번째 결함처럼 보였다.

**아니었다.** 도달 가능한 공간을 훑었다:
- 무작위 자모 봉지 20000개 → 폭 초과 **0회**, 최장 434 px
- 등록 단어마다 자모 일부 제거 + 군더더기로 6810개 조합(무작위가 못 만드는 3음절 목표를
  겨냥) → 폭 초과 **0회**, 최장 428 px

도달 가능한 최장은 428~434 px, 한계 479 px. **잘림 결함은 없었다.**
`tools/BeltTextWidth.gd` 의 기본 후보 목록을 **관측된 실제 최장값**으로 고쳤다 — 거짓 경보를
내는 프로브는 무시하게 된다.

### 만든 도구: `tools/BeltTextWidth.gd` (+ `.tscn`)
벨트 헤더 미리보기 라벨의 **실제 폭**을 재고 후보 문장의 여유를 px 로 찍는다.
- **전체 씬을 띄운다.** 헤더 폭은 버튼 개수에 따라 달라진다: 유물 없음 **568 px**,
  유물 있음 **479 px**. 비교 줄은 유물 보유자만 보는 줄이라 479 가 유일하게 중요한 값이다.
- `-- text=...` 로 임의 문장을 잴 수 있다.
- `tools/Shot.gd` 에 `relic=id1,id2` 옵션 추가(유물이 헤더 버튼을 늘려 라벨을 좁히므로,
  유물을 쥐여 준 캡처가 필요했다).

**선정 근거(지배 명령)**: "로직은 이미 존재하지만 표현이 부족한 사건을 우선 찾아라".
방어도는 `take_damage` 에서 완전히 동작하는데(피해를 먼저 먹는다) 화면에는 **거의 아무것도**
없었다. 새 콘텐츠가 아니라 이미 있는 규칙의 표현을 고치는 일이다.

### 측정한 결함 3가지
1. **`Juice` 의 `"shield"` 종류는 죽은 분기였다.** 색(`Color(0.65,0.72,0.95)`)과 크기가
   정의돼 있었지만 **아무 호출자도 그 종류를 돌려주지 않았다** — 입력 전수 스캔 결과 `아니오`.
2. **방어도가 전부 먹은 타격이 실제 HP 피해와 똑같이 보였다.** 40 방어도에 30 피해 →
   흰 숫자 `30`. HP 를 30 깎은 타격과 **구분 불가**. 플레이어는 타워가 잘 하고 있다고 읽는다.
3. **방어도가 바의 34.8% 인데 1px 테두리뿐.** HP 바는 36×6 px 이므로 1px 테두리가 먹으면
   채움은 4px — 사실상 안 보인다. `armored` 는 **모든 막에 한 마리씩** 나오므로 드문 일이 아니다.

### 고친 방법
- `Palette.SHIELD = #A6B8F2` 신설(피해 숫자 + HP 바가 **같은 색**을 나눠 쓴다).
- `EnemyUnit._damage_kind(absorbed, amount, dealt, mult)` **순수 함수** 신설 —
  `amount > 0 and absorbed >= amount` 면 `"shield"`. `take_damage` 가 이걸 부른다.
  `_hit_kind` 는 그대로 두고 **감싸기만** 했다(기존 분류 보존).
  이름을 `_test_` 로 시작하지 않게 둔 것은 의도적 — 가드가 실제 값으로 직접 부를 수 있어야 한다.
- `_refresh_hp_bar_color()`: 방어도가 남아 있으면 채움·테두리를 방어도 색으로.

### 이 색을 쓸 수 있는 **근거**(주석 + 테스트로 잠금)
`take_damage` 는 `absorbed = minf(shield, amount)` → **`shield > 0` 이면 `hp == max_hp`**.
즉 방어도가 버티는 동안 HP 심각도 축(초록/노랑/빨강)은 **퇴화**해 있어 같은 통로를 방어도가
써도 축이 충돌하지 않는다. 이 불변식을 테스트가 20대 동안 매 타격 검사한다.
나중에 방어도 재생 같은 걸 넣어 불변식이 깨지면 그 테스트가 먼저 실패한다 — 그때는 색이 아니라
'방어도 구간' 을 따로 그려야 한다.

### 판단 하나 (되돌릴 수 있음)
**방어도가 전부 먹은 '약점' 타격도 `"shield"` 로 말한다.** HP 에 닿지 않은 피해에 '약점' 이라는
품질을 붙이면 그게 곧 거짓말이다. 방어도는 몇 대 만에 벗겨지므로 교훈은 곧 다시 온다.
(테스트가 이 판단을 고정해 두었다)

### 곁다리로 발견해 고친 것 — **테스트 하네스 결함(선행)**
`_make_tower()` 가 `WordTower.new()` — 씬이 아니라 **맨 스크립트 인스턴스** — 를 만들어
자식 노드가 0개였다. 호출자가 `add_child()` 하는 순간 `_ready()` 의 `@onready` 6개가 전부 실패:
`IconContainer`, `IconContainer/IconSprite`, `LabelBigWord`, `LabelWord`, `RangeCircle`, `BtnSelect`
→ **실행당 ERROR 66줄**. 그리고 더 나쁜 것: 그 테스트는 화면에 존재하는 타워가 아닌 것을
검증하고 있었다. `WordTowerScene.instantiate()` 로 바꿨다(`setup_tower` 가 전부 `if node:` 로
가드돼 있어 트리 진입 전 호출도 안전 → 순서는 안 바꿈).
결과: **66 → 0**. 전체 실행에서 `Node not found` 0건.

### 내가 밟은 함정 (기록)
- **"기준선 측정" 이 무의미했다.** `git stash push -- godot/tests/test_wave_balance.gd` 는
  파일 **전체**를 HEAD 로 되돌린다. 이 저장소의 작업본은 1648줄, HEAD 판본은 149줄 스텁이라
  의심하던 테스트 자체가 사라진 상태에서 `0` 이 나왔고, 나는 그걸 근거로 **엉뚱한 범인**
  (내 가드)을 지목했다. → 잡음은 **스택 트레이스로** 귀속시켜야 한다. 66건 전부
  `_test_tower_pair_synergies_reward_matching_forms` (1204~1259) 를 가리켰고 내 가드는 0건이었다.
- **색 변화를 눈으로 판정하려다 틀릴 뻔했다.** 중갑병을 잘못 골라 크롭해서 전/후가 **똑같아
  보였다**. 프레임에서 `Palette.SHIELD` 정확한 픽셀값을 **검색**하니 before 0px / intact 164px /
  broken 0px — 고쳐져 있었다. bbox 로 위치를 잡고 그 주변을 크롭해야 한다.
- **`shield/N` 을 N번 때리면 부동소수 잔여가 남는다.** `take_damage` 에 클램프가 없어
  `shield = 1e-16 > 0` 이면 바 색이 안 바뀌어 '이후' 프레임이 '이전'과 같아진다.
  마지막 한 대를 `e.take_damage(e.shield, false)` 로 — `amount == shield` 면 정확히 0.0.
- **주석의 44% 는 오기였다.** `armored` 는 `hp 1.5, shield 0.8` → 바 전체 2.3 중
  **0.8/2.3 = 34.8%**. 44% 는 `hp = 1.0` 으로 잘못 놓고 계산한 값. 주석 3곳 + 독블록을 정정.

### 만든 도구
`tools/Shot.gd` 에 `breakshield=N` 추가 — 방어도를 N번의 타격으로 **정확히** 벗긴다.
마지막 한 대가 방어도를 딱 0 으로 만들어 **HP 는 한 대도 안 깎인** '방어도가 방금 벗겨진'
순간을 찍을 수 있다. `burn=` 과 같은 원칙으로 실제 입구(`take_damage`)를 지난다.

### 검증
- `test_wave_balance`: 새 가드가 순수 분류기 6건 + 색 구분 6건 + 실제 경로 라벨 1개/색/값 +

- 전체 6개 스위트: **rc=0, SCRIPT ERROR 0건, `!!` 0건**, `Node not found` **0건**.

- 캡처: `docs/design/screenshots/enemy_shield_before_after.png` (3단: 이전 초록바 / 방어도 색 /
  벗겨진 뒤 65%). 임시 프로브 `tests/probe_shield.gd`·`.tscn` 삭제.

### 남은 것 (이 항목에서 파생)
- HP 바는 `hp + shield` 를 **한 덩어리**로 그린다. 그래서 방어도가 벗겨지는 순간 바가

  동작이지만, '방어도 구간' 을 따로 그리는 안은 디렉터 판단 사항.

## (U) 슬롯 힌트가 '단어 없음' 일 때 **서 있는 것을 말하지 않던** 문제

**선정 근거(지배 명령)**: "특히 로직은 이미 존재하지만 표현이 부족한 사건을 우선 찾아라".
`parsed_slots()` 는 슬롯이 '미지의 활자' 를 세우고 있다는 것을 **정확히 알고** 있고,
그 타워는 실제로 기본 탄환을 쏘고 화면에 서 있다. 그런데 힌트 한 줄은 그 사실을 안 말했다.

### 측정 (도달 공간 전수 — 먼저 훑었다)
봉지는 `HangulEngine.ALL_DRAW_POOL` = **단순 자모 15종뿐**(ㄱㄴㄷㄹㅁㅂㅅㅇㅈ ㅏㅓㅗㅜㅡㅣ).
그 15종으로 1~5장 중복조합 **15503개**를 만들어 `buildable_words_for` 를 돌렸다:

| | 건수 | 비율 |
|---|---|---|
| 헤더가 "만들 수 있는 단어가 없어요" 를 띄우는 봉지 | 3924 | 25.3% |
| └ 슬롯이 **비어** 있는 경우 | 2462 | 62.7% |
| └ 슬롯이 **미지의 활자**를 세우고 있는 경우 | **1462** | **37.3%** |
| └ 슬롯이 **등록어**를 세우고 있는 경우 | **0** | — (그런 모순은 도달하지 않음) |

즉 **25.3%** 에서 이 줄이 뜨고, 그중 **9.4%**(전체의) 는 "일하고 있는 타워를 아무것도 아닌 것처럼"
말하는 경우였다.

### 고친 방법
`_slot_hint_text` 의 `target == ""` 분기를 `_no_target_text(slot_index)` 로 뺐다.
`parsed_slots()` 로 **슬롯이 서 있는 음절**을 보고 두 상태를 가른다:
- 서 있는 게 있으면 → `1번 슬롯: 가 (미지의 활자) — 기본 탄환만 나가요`
- 비어 있으면 → `1번 슬롯: 지금 타일로 만들 수 있는 단어가 없어요` (그대로 — 이때는 정직하다)

서 있는 음절을 적는 것은 답을 흘리는 게 아니다(화면에 이미 서 있는 글자다).
'미지의 활자' 는 이 게임이 이미 쓰는 말이다 — `HangulStreamParser.make_unknown_word_data`,
`CardSystem`, `LexiconModal`. **벨트 헤더만 그 말을 안 쓰고 있었다.**

### 도달 불가였던 가짜 결함 (중요 — 또 밟을 뻔했다)
처음엔 더 심각한 걸 찾았다고 생각했다: 벨트가 `[ㄱ, ㅐ]` 를 들면 `parsed_slots()` 는
**등록어 `개`** 를 세웠다고 읽는데(단어번호 15, damage 9), 힌트는 "단어가 없어요" 라고 말했다.
모순처럼 보였다.

**아니었다.** `_tiles_for_word("개", ["ㄱ","ㅐ"])` 는 못 찾지만
`_tiles_for_word("개", ["ㄱ","ㅏ","ㅣ"])` 는 찾는다. `required_jamo("개")` 가 겹모음 ㅐ 를
**구성 자모 ㅏ+ㅣ 로 펼쳐서** 두 장을 요구하기 때문이다(`get_word_syllable_slots` 의
`[[["ㄱ"],["ㅏ","ㅣ"]]`).

그런데 **ㅐ 타일은 얻을 수 없다**: 봉지에 없고, `_on_tile_swap_requested` 도
`VOWEL_POOL`(단순모음만) 에서 뽑는다. `VOWEL_COMBINATIONS` 에 `"ㅏ+ㅣ":"ㅐ"` 가 있어도
그 표를 쓰는 곳은 **파서와 `get_word_syllable_slots` 뿐** — 두 장을 한 장으로 합치는 동작은 없다.
그래서 `[ㄱ,ㅐ]` 는 합성 경로가 없는 상태였고, 전수 조사에서 **등록어 모순 0건**으로 확인됐다.

교훈: **모순을 찾으면 먼저 도달 가능한지 훑어라.** (앞서 나침반 항목에서 같은 함정을 밟았다)

### 내가 밟은 함정 (기록)
- **버튼을 안 누르고 라벨을 읽었다.** `_slot_hint_text` 는 `slot_targets` 를 읽는데,
  그 값은 `_show_slot_hint`/`_show_all_hints` 만 채운다. 첫 프로브는 `clear_slot_locks()`
  직후에 읽어서 **모든 케이스가 '목표 없음' 분기**로 나왔고, 그걸 '결함' 으로 읽을 뻔했다.
  → 힌트 줄을 읽으려면 **힌트를 실제로 눌러야 한다.**
- **`buildable_words_for(owned: Array[String], …)` 는 타입이 맞아야 한다.** 무타입 `Array` 를
  넘기면 `Invalid type in function … does not have the same element type as the expected typed
  array argument` — 그리고 SCRIPT ERROR 라 `quit()` 이 안 돌아 **프로브가 타임아웃까지 매달린다**(rc=124).
  `var bag: Array[String] = []` 로 받아라.
- **`render_belt()` 를 루프 안에서 부르지 마라.** 15503개 전수가 5분을 넘겨 잘렸다.
  `parsed_slots()` 는 순수 파싱이라 싸다 — 렌더만 빼면 2분이다.
- **헤더 폭은 전체 씬에서 재라.** 벨트만 단독으로 띄우면 503 px 가 나오는데,
  실제 `TowerDefenseMain` 에서는 유물 없음 568 px / **유물 있음 479 px** 다.
  `tools/BeltTextWidth.gd` 를 쓴 이유가 그것이다.

### 검증
- 새 가드 `_test_no_word_hint_still_names_what_is_standing` (test_tower_traits):
  (1) `[ㄱ,ㅏ]` 가 정말 '단어 없음' 이고 슬롯이 `가` 를 세우는지 먼저 못 박고,
      줄이 `가` 와 `미지의 활자` 를 말하며 "만들 수 있는 단어가 없어요" 를 **안 쓰는지**,
  (2) 빈 슬롯에서는 두 줄이 **서로 다르고** 옛 문장이 남는지,
  (3) 두 줄 다 479 px 안에 들어가는지(라벨이 `clip_text = true` 라 조용히 잘린다).
- **가드 주입 → 3개 실패** 확인. 결정적 증거:
  `An empty slot and a slot standing on 미지의 활자 must not read the same (both '…없어요')`
  → 주입 제거 → 통과.
- 폭 실측(`tools/BeltTextWidth.gd`, 전체 씬): 두 줄 다 **312 px**, 유물 보유 한계 479 px (여유 167 px).
  `DEFAULT_CANDIDATES` 에 두 형태를 추가했다.
- 전체 6개 스위트: **rc=0, SCRIPT ERROR 0건, `!!` 0건, `Node not found` 0건.**
- 캡처: `docs/design/screenshots/slot_hint_no_word_before_after.png` (3단: 이전 / 이후 / 빈 슬롯).

### 남은 것 (이 항목에서 파생)

## (V) 상점 유물 설명이 **실제 효과의 절반을 말하지 않던** 문제

**선정 근거(지배 명령)**: "이미 존재하는 게임플레이가 충분히 전달되지 않거나 완성도를
떨어뜨리는 요소". 상점 설명은 **사는 사람이 읽는 유일한 계약**인데, 두 유물이 설명에 없는
효과를 조용히 주고 있었다. 효과 자체는 의도된 설계(`cat` 조건 + 전용 라벨이 따로 있음)라
효과를 지우는 게 아니라 **설명이 그 효과를 말하게** 고쳤다.

### 찾은 방법 — 기계적 감사
`_test_every_shop_relic_has_an_effect` 는 **"효과가 하나라도 있으면 통과"** 만 본다.
설명과 효과가 같은 말을 하는지는 **아무도 안 봤다.** 그래서 프로브로 유물 27개를
켠 타워/끈 타워의 스탯 차이(`damage_multiplier`, `attack_interval`, `attack_range`,
`crit_chance`, `bonus_targets`, `burn_duration_multiplier`)로 대조했다.

### 발견 2건 (둘 다 골드를 주고 사는 물건)
| 유물 | 값 | 설명 | 실제 |
|---|---|---|---|
| **천리안의 룬** | 30G | "모든 타워의 공격 범위 +15%" | 범위 +15%(전역, `DefenseField`) **+ 무기 타워 치명타 +10%**(`WordTower`) |
| **선봉의 깃털** | 35G | "각 타워의 첫 공격 피해 2배" | 2배 **+ 소환 타워는 3배** |

둘 다 **테스트 커버리지가 0** 이었다(새 가드가 첫 커버리지).

### 고친 방법
- 상점 설명에 예외를 명시: `(무기 타워는 치명타 +10%)`, `(소환 타워는 3배)`.
- 툴팁 라벨도 다른 라벨들처럼 효과를 말하게: `천리안 조준` → `천리안 조준 (치명타 +10%)`,
  `소환 선봉` → `소환 선봉 (첫 공격 3배)`. (다른 라벨은 이미 `폭발의 뇌관 (+25% 피해, 대상 +1)`
  처럼 숫자를 적고 있었다 — 이 둘만 안 적고 있었다.)
- `WordTower.attack_target` 안에 인라인으로 있던 첫 공격 배수를
  **순수 함수 `first_strike_multiplier()`** 로 떼어 냈다. 테스트가 실제 값으로 부를 수 있어야
  **설명과 코드를 함께** 잠글 수 있다(`_damage_kind` 와 같은 이유·같은 방식).

### 새 가드는 **양쪽을 함께** 잠근다
`_test_relic_descriptions_match_their_hidden_extras`:
- 효과가 사라지면 실패 → `천리안의 룬 must still give weapon towers its crit bonus — or the
  shop text must drop it`
- 설명이 되돌아가면 실패 → `must state the crit bonus it actually gives`
- 무기 외 타워에는 치명타가 안 붙는지, 첫 공격 뒤에는 배수가 사라지는지, 유물이 없으면
  배수가 1.0 인지까지 확인.
**주입 2종으로 양방향 실패를 확인**했다(효과 제거 → 2건 실패 / 설명 되돌림 → 1건 실패).

### 곁다리로 고친 **테스트 헬퍼 결함 (선행)**
`_make_tower` 가 스텁 필드를 만들자마자 `field.free()` 했다. Godot 은 Node 를 free 하면
그 참조를 null 로 만들므로 **`setup_tower` 이후에 `field_ref` 를 읽는 질문이 전부 조용히
'유물 없음'** 이 됐다. `first_strike_multiplier()` 를 처음 만들었을 때 그래서 3.0 이 아니라
1.0 이 나왔다 — 즉 **테스트가 틀린 답을 정답처럼 보여 주고 있었다.**
`_stub_fields` 배열에 담아 두고 테스트 끝에 한꺼번에 free 하도록 고쳤다.
(안 치우면 종료 시 `resources still in use` 줄이 늘어난다 — 그것도 함께 없앴다.)

## (W) 디렉터 지시 — "설명과 코드를 일치시켜줘. 설명에 맞춰" (완료)

**(V) 의 결론이 뒤집혔다.** (V) 에서는 코드가 맞고 설명이 틀렸다고 보고 **설명을 고쳤는데**,
디렉터 지시는 반대였다: **설명이 계약이고, 코드를 설명에 맞춘다.**
→ 그래서 (V) 에서 추가한 문구는 전부 **원래 문구로 되돌리고**, 대신 **코드에서 숨은 효과를 지웠다.**

### 바뀐 것 (설명 → 코드 방향)

| 대상 | 이전 코드 | 이후 코드 | 설명 |
|---|---|---|---|
| 천리안의 룬 | 범위 +15% **+ 무기 치명타 +10%** | 범위 +15% 만 | "모든 타워의 공격 범위 +15%" |
| 선봉의 깃털 | 2배, **소환은 3배** | 모든 타워 2배 | "각 타워의 첫 공격 피해 2배" |
| 신속의 나침반 | 간격 ×0.8 (=속도 +25%) | `speed_pct_to_interval(20)` = 간격 ÷1.2 | "공격 속도 +20%" |
| 민소리 깃털 | 간격 ×0.82 (=+21.95%) | `speed_pct_to_interval(18)` | "받침 없는 타워 공격속도 +18%" |
| 모음 공명석 | 간격 ×0.8 (=+25%) | `speed_pct_to_interval(20)` | "같은 모음이 반복되면 공격속도 +20%" |
| **무받침 풍경** | 간격 ×0.88 (=+13.64%) | `speed_pct_to_interval(12)` | "양쪽 공격속도 +12%" |

**핵심 규칙**: 공격속도 = 초당 공격 횟수. N% 늘리려면 간격에 **역수**(`1/(1+N/100)`)를 곱한다.
`interval *= 0.8` 은 +25% 다. `WordSynergy.speed_pct_to_interval(pct)` 한 곳에서만 만든다.

### 새로 찾은 것 — **네 번째 유물(무받침 풍경)** 을 가드가 스스로 찾아냈다
내가 손으로 만든 목록에는 셋뿐이었다. 새 가드는 유물 목록을 **설명에서 정규식으로** 찾는다
(`공격\s*속도\s*\+\s*(\d+)\s*%`). 그래서 무받침 풍경(+12%)이 저절로 걸렸다 —
**목록을 손으로 적으면 이렇게 빠진다.** 무받침 풍경은 `DefenseField._apply_tower_synergies`
(인접 배치)에서 걸리므로 타워 하나로는 잴 수 없어, 실제 필드에 두 타워를 붙여 재는 경로를
따로 만들었다(`_adjacent_pair_interval` — 유물 없이/있이 두 번 재서 차이를 본다).

### 가드 (양방향 증명 완료)

`_test_attack_speed_relics_honour_the_percent_in_their_text` (test_wave_balance):

**(1) 오디오 — "재생 중인 채로 프로세스가 끝나면 샌다"**

  4번 돌려 `0 / 1 / 1 / 1` 을 봤다. 그래서 "고쳤다/안 고쳤다" 를 1회 실행으로 판단하면 속는다.

- **통한 방법**: 테스트가 MainScene 을 세우는 **동안만** `SoundEngine.muted = true`.

  → `tests/test_wave_balance.gd`, `tests/early_wave_playtest.gd` 둘 다 적용. 이후 4/4회 0개.
